## 8. Clued 核心产品原则：AI 连续性

### 8.1 用户痛点

AI 即使已经参与了一个长期项目，也可能在会话、模型、Agent、工具、设备或部署目标切换后丢失状态，迫使用户反复解释“我是谁、项目是什么、做到哪了、为什么这样决定、下一步是什么”。

**Clued 就是为了解决这个问题。** 这不是内部工作流程优化，而是产品的核心买点与验收标准。

### 8.2 核心承诺

> 用户不应重复解释已经被 Clued 捕获的上下文。AI 在授权范围内应自动恢复：用户是谁、当前工作是什么、进度停在哪里、决策为什么形成、实际系统目标是什么、下一步该做什么。

- 品牌表达：`Clued — One you. Every AI.`
- 产品关系：`Clued by Pixel Gravity`
- Clued 是用户拥有、可授权、可审计的统一个人上下文层。
- Clued 不是公开个人主页、无差别保存全部聊天的档案库，也不把用户数据用于模型训练。

### 8.3 必须保存的工作状态

Clued 不得只保存孤立事实，必须保存可恢复的结构化工作状态：

1. 稳定事实和用户偏好。
2. 已作出的决策及其理由。
3. 当前项目状态和真实系统目标。
4. 已执行动作、结果和证据。
5. 失败、阻塞、矛盾和已撤回结论。
6. 一个明确的下一步动作。
7. 信息来源、授权范围、时间和置信度。

### 8.4 连续性生命周期

1. **Restore：** 新会话/新 Agent 开始任务时，先恢复权威上下文和最新已验证状态。
2. **Execute：** 执行期间记录目标、操作、结果、证据和错误。
3. **Commit：** 结束前原子写回完成项、阻塞项和下一步。
4. **Resume：** 之后任一已授权 AI、设备或工具都能接着做，不要求用户重新讲述。

### 8.5 产品验收标准

一个全新的 AI 会话，在只获得用户授权和 Clued 访问后，必须能正确回答：

- Clued 当前是什么、发布范围是什么？
- 最近一个已验证事实是什么？
- 最近执行了什么，结果和证据是什么？
- 哪个结论曾被撤回？
- 当前被什么阻塞，为什么？
- 唯一下一步是什么？
- 这些结论对应哪个来源和部署目标？

只要用户还需要重复可获得的上下文、AI 混淆两个部署目标、静默覆盖矛盾，或把计划当成完成项，验收即失败。

## 12. 2026-08-23：跨厂商自动连续性第一条可执行纵切

### 12.1 本次产品裁决

- **Supabase Auth/PostgreSQL 继续是唯一 Canonical Context Store。** Cloudflare Worker 是跨厂商 Edge/MCP 入口，不另建第二份事实源。
- 每个 AI 使用独立、可撤销、带 Scope 的 `Clued Binding Token`；原始令牌只显示一次，服务端只保存 SHA-256 哈希。
- 自动连续性协议固定为：`Restore → Append authoritative events → Atomic Checkpoint → Resume`。
- 检查点使用 `base_version` 乐观并发和 PostgreSQL 事务级 advisory lock；过期版本返回显式 conflict，禁止静默覆盖。
- 本阶段搜索仅为确定性 lexical search；不启用 R4 语义召回，保持既有 `NO-GO / UNRELEASED` 裁决。
- 所有 Restore、Append、Checkpoint 都生成不可变 Audit Receipt，并保留 Binding、版本、对象和时间来源。

### 12.2 已实现代码

Clued Sites 源码提交：`72c26f91f865aff64bd0ca690b18406f9c047443`。

- `GET|POST|DELETE /api/bindings`：登录用户列出、创建、撤销 AI Binding。
- `GET /.well-known/oauth-protected-resource/mcp`：受保护资源与 Scope 元数据。
