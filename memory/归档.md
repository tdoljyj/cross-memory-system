## tracking ref 写入缺陷：根因与止血（2026-08-15 ~ 08-16）

- **症状**：fetch 显示更新 origin/main 成功但引用不持久，status 幻影 ahead / gone，update-ref 返回 0 但不写文件；一层目录 ref 正常、两层及以上失败，对象传输不受影响
- **根因实锤（00:35 GIT_TRACE2 cmd_ancestry）**：Bash / PowerShell 通道 git 都被 sandbox-cli.exe 包裹（git.exe ← bash/powershell.exe ← sandbox-cli.exe ← WorkBuddy.exe）→ 写入走沙盒 overlay；沙盒拦的是 git 写 ref 的 lockfile+rename 原子写，两层子目录写不进且 exit 0 静默失败（还清空父目录）；Python os.makedirs+open 直写成功（不走 rename）
- **排除项**（全复现失败）：git 版本（官方 2.55.0.3 / 2.54.0.windows.1 便携版 / PortableGit 2.55.0.windows.3）、仓库损坏（全新 init）、shell 环境（Bash + PowerShell）→ 锁定沙盒 overlay
- **复发**：21:15 / 23:30 / 23:57 / 00:03 四次，机制一致；防复发 config（fetch.autoMaintenance=false / gc.auto=0 / maintenance.auto=false / gc.pruneExpire=never）不能阻止
- **数据零风险**：fetch / push / commit 对象传输正常，只有 tracking ref（状态指针）写不进；status 的 ahead / behind / gone 不可信，一切以 ls-remote 为准
- **根治三选**：① WorkBuddy 开 Full access（最彻底）② 工作流不依赖 tracking ref（显式 merge（非 rebase）origin main / push origin main，status gone 是 cosmetic，零成本；早期曾用 pull --rebase）③ Python 直写 ref 兜底（已封装 sync-memory.py）。推荐 ② 为主 + ③ 兜底

## 收敛策略修正 rebase→merge + union driver 落地（2026-08-16 01:50，WorkBuddy）

- 实测（隔离仓库 E1~E4）：`.gitattributes` 的 `merge=union` 无 driver 是 no-op，归档.md 末尾追加（常态）即冲突；更严重的是 rebase + union driver 会 **exit 0 假成功 + 静默丢单边内容**（比冲突危险）。正确组合 = `.gitattributes merge=union` + `git config merge.union.driver 'git merge-file --union %A %O %B'` + 收敛用 `git merge`（非 rebase）
