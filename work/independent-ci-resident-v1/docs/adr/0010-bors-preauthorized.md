# ADR 0010：长远走 bors 式列车（已预授权）

- 状态：Owner 已预授权。第 28 代已实现代码（[ADR 0018](0018-bors-landing.md) 落地与二分，[ADR 0019](0019-train-batch-member-chain.md) 批量成员链），开关默认 `github-merge`。按 Owner 决定，满足下面的触发条件、做完 ADR 0018 第 8 节的上线前提之后再改成 `push`。
- 日期：2026-11-07
- Owner Decision：`9e2511fe` 第 6 项；预授权记录在 Task `7d86cf41`
- 档案：没有，这是新设计。仓库里相关的方案比较见 `development/contracts/execution-admission/ADR-EA-001-MergeAdmissionPolicy.md`。

## 背景

strict 永久开以后，main 每移动一次，排在后面的每个 PR 都要合一次 main，再重跑一遍 CI。PR 一多，等待时间会随数量线性增长。

bors 式的做法有三点：

- 列车自己把测过的合并提交快进推上 main；
- 一次测一批，失败时用二分法定位是哪个 PR；
- 车头还没测完时，就预测结果，并行测后面的 PR。

## 决定

PR 多起来时改用 bors 式列车。Owner 已预授权，时机合适就直接做，包括下面列出的规则修订。实施前仍要在看板上告知；生产迁移和权限变更按各自的批准流程走。

**触发时机**（满足任一条即可）：

- 合并队列里常态有 ≥ 3 个 PR 在等；
- PR 从就绪到合入的平均等待时间 > 1 小时，并且持续一天；
- strict 永久开模式和中期提速（一批一次换手、按树缓存）都已落地，而且主线空闲。

**需要的改动**：

- App 增加 `contents: write` 权限；
- 规则集给 App 开 bypass；
- 禁止从 PR 页面直接合并：加一项只有列车能满足的必需检查，或用等效手段；
- Owner 修订 #292 的规则"自动化也经 PR、bypass 为空"；
- 拆除不再需要的部分：全量扫描、撤绿台账、单绿证明等。

## 理由

- 吞吐目标是批量合并后每小时 ≥ 15 个 PR（Task `bf57ff10`），一次只合一个的列车做不到。
- bors-ng 本身已停止维护，所以在现有列车上演进，不引入新系统。

## 后果

- 落地后，合入方式从"GitHub 按 merge 方式合"变成"列车快进推送"。信任边界随之移到列车的推送身份上，这部分需要单独设计和独立审查。
- 在那之前，按 [ADR 0007](0007-strict-permanent.md) 运行。
