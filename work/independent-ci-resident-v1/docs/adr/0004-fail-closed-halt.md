# ADR 0004：白名单分类，认不出就 HALT

- 状态：生效
- 日期：2026-10-21
- Owner Decision：`0d84ddbb` 第 4 项（失败分类按白名单）；`4f5f35d3`（常驻规则：发现的缺陷必须修，不得放过）
- 档案：DESIGN §6.3、§6.5、§16.3

## 背景

常驻执行器没人盯着。遇到没见过的失败时，如果继续往下跑，就可能在一端不干净时开始下一批，或者把"可能已发布"当成"没发布"。

## 决定

- 失败分三类：
  - NOT_ADMITTED：只在第 1 段，释放；
  - CLEAN：白名单码，且两端证明静止，只改名归档，烧号后继续；
  - UNKNOWN：其余一切，烧号，HALT，现场不动。
- 静止证明在失败时**从两端现取**，不沿用阶段的自报。
- 释放还是烧号，由机器可读的失败对照表 `src/failure-table.json` 决定。表里没有的组合一律当未知。
- HALT 只升不降。只要还有未归档的未知现场就保持 HALT。只有 Owner 提权写复位请求才能清除；复位由服务自己实测静止、只改名归档，从不重跑出事的 head。

## 理由

- 白名单的错误方向是"多停一次"，黑名单的错误方向是"漏过一次"。对能合入 main 的系统，前者便宜得多。
- 归档只改名、不删除，保留了查因的全部现场。

## 后果

- 每一种新出现的失败第一次都会 HALT。
- 按 `4f5f35d3`，每次 HALT 的根因都要登记并修掉。修法通常是证明某类失败"确实干净"之后，把它加进白名单，或者改成批次内原地重跑（DESIGN §49–§59 都是这样来的）。
- 自动恢复从不写、不清除 `HALT.json`。
