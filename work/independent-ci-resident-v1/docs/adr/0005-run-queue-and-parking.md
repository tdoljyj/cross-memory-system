# ADR 0005：执行器自有排队表；第 8 段停靠

- 状态：生效
- 日期：2026-10-23（第二期第 1、2 步）
- Owner Decision：`6c69755a`、`e1e19e2e`（额度第二期；`e1e19e2e` 第 4 项：非列车模式第 8 段改为停靠）、`c32676f4`（等托管结果时不占住执行器）
- 档案：DESIGN §17、§18

## 背景

起初执行器按触发文件先进先出，第 8 段在段里最长等 45 分钟。一个 PR 在等合并队列，就占着整台机器；同一 PR 的新提交和旧批次互相打架；释放和重试没有统一的节奏。

## 决定

- **排队表**：执行器自己维护 `state\queue\queue.json`，每个 PR 一行，只决定"下一个试谁"。能不能跑永远以账本为准。新提交替换还在等的旧提交；正在跑的批次在安全点凭实时读结束。
- **停靠**：一批在两个停靠点上不占执行器：
  - A：第 1 段之后等托管；
  - B：第 1–7 段之后、第 8 段之前。
  - 停在 B 的批次按"尝试"反复跑第 8 段，每次最多 90 秒；
  - 有退避、名额和次数上限；在合并队列队首时 1 分钟后再试。
- **额度与熔断**：全部从账本推算；熔断按失败位置判断能否关闭。

## 理由

扫描（第 1–7 段）和等合并位（第 8 段）是两种完全不同的等待。把后者变成停靠，机器就能在等待期间跑别的 PR。

## 后果

- 多个 PR 可以同时停在 B，第 8 段只在快到队首时频繁尝试。
- 停在 B 的批次可能占住它那一行，挡住同一 PR 新 head 的车头批次。现场 #1035 就是这样卡住的，已在 `c933238b5` 修复（DESIGN §65.9）。
