# ADR 0005：执行器自有排队表；第 8 段停靠

- 状态：生效
- 日期：2026-10-23（第二期第 1、2 步）
- Owner Decision：`6c69755a`、`e1e19e2e`（额度第二期；`e1e19e2e` 第 4 项：非列车模式第 8 段改为停靠）、`c32676f4`（等托管结果时不占住执行器）
- 档案：DESIGN §17、§18

## 背景

起初执行器按触发文件先进先出，第 8 段在段里最长等 45 分钟。一个 PR 在等合并队列，就占着整台机器；同一 PR 的新提交和旧批次互相打架；释放和重试没有统一的节奏。

## 决定

- **排队表**：执行器自己维护 `state\queue\queue.json`，每个 PR 一行，只决定"下一个试谁"。能不能跑永远以账本为准。新提交替换还在等的旧提交；正在跑的批次在安全点凭实时读结束。
- **停靠**：一批在两个停靠点上不占执行器：
  - A：第 1 段之后等托管；
  - B：第 1–7 段之后、第 8 段之前。
  - 停在 B 的批次按"尝试"反复跑第 8 段，每次最多 90 秒；
  - 有退避、名额和次数上限；在合并队列队首时 1 分钟后再试。
- **额度与熔断**：全部从账本推算；熔断按失败位置判断能否关闭。

## 理由

扫描（第 1–7 段）和等合并位（第 8 段）是两种完全不同的等待。把后者变成停靠，机器就能在等待期间跑别的 PR。

## 后果

- 多个 PR 可以同时停在 B，第 8 段只在快到队首时频繁尝试。
- 停在 B 的批次可能占住它那一行，挡住同一 PR 新 head 的车头批次。现场 #1035 就是这样卡住的，已在 `c933238b5` 修复（DESIGN §65.9）。

## G4：认领等待的预算（2026-11-16）

根因证据（基线 `7fe6eb22d7e5ade299c7d536239b7e86d7cc387a`）：`src/queue.mjs:419–420` 将认领拒绝固定为 10 分钟 `BACKOFF`；`src/queue.mjs:338` 将到期行选为 `backoff-retry`；`src/ledger.mjs:509,515` 只按 `waiting-retry` 分离等待计量，认领拒绝因此仍占普通评估额度。

`CLAIM_NOT_CURRENT` 的安全未执行释放归入现有 `waitingRetriesPer24h`，首次拒绝也计一次；不占普通评估或 head 释放额度。账本按释放结果识别，历史 `queued`、`backoff-retry`、`new-trigger` 记录也按此重算，无需改写账本。已烧号或清理未确认的失败不享受该豁免。

认领等待使用 `WAITING`，复用 10→20→40→80→120 分钟退避及 24 小时等待边界；旧队列里的认领 `BACKOFF` 仍能接续。普通 PR 编辑不能缩短退避或改用普通评估预算。受保护的 Native 观测确认认领或授权发生变化时，仍立即走 `new-trigger`，跳过冷却和等待预算；原有真实评估、重新评估和执行权限检查保持有效。

等待预算满只推迟等待行，真实评估预算满仍允许到期等待重查。测试覆盖队列、账本、执行器的完整离线路径，以及重启兼容和历史额度重算；生产节点须在通用包上线后按同一 head 晚认领场景另做实测。
