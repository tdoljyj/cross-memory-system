Cross Memory System vNext：跨会话记忆系统核心架构

目标：将“每次开头强制加载记忆、结尾强制上传”改造成真正的按需读写型跨会话记忆系统。

>

核心原则：默认不加载个人记忆；只有当当前问题与个人身份、偏好、历史项目、个人经历、约束等存在明确关联时才进行最小必要召回；只有本轮产生新的个人相关信息或修改时才持久化。

---

一、核心结论

原机制：


每次会话开始
    ↓
强制加载全部记忆
    ↓
AI回答
    ↓
每次会话结束
    ↓
强制上传全部记忆

应彻底废弃。

新的核心流程：


用户请求
   ↓
Memory Router
   ↓
判断是否存在“个人记忆相关性”
   │
   ├── 无关 → 不访问 Memory
   │
   └── 相关
        ↓
     Recall Planner
        ↓
   只召回必要记忆
        ↓
   AI Context
        ↓
   正常回答
        ↓
   Memory Change Detector
        ↓
   是否产生新的个人信息/修改？
      │
      ├── 否 → 不写
      │
      └── 是
           ↓
       Candidate Memory
           ↓
       Validation
           ↓
       Versioned Commit
           ↓
       Sync / Cache Invalidation

核心思想：

不要把“按需加载”理解成“发现相关后加载全部个人记忆”。

>

应该采用：请求级记忆路由 → 最小必要召回 → 分层注入 → 本轮产生变化才写回 → 版本化提交 → 同步/缓存失效。

二、当前架构需要重点审查的问题

严重程度：

  • **P0**：必须解决，否则可能导致核心数据错误
  • **P1**：高优先级，影响核心体验
  • **P2**：中等问题，影响性能/稳定性
  • **P3**：优化项

    • P0-1：全量加载记忆

    问题位置

    
Session Start
    ↓
Load All Memories

    影响

    1. 无关问题也读取个人数据。

    2. 增加上下文 token。

    3. 增加延迟。

    4. 增加模型受到无关历史信息干扰的概率。

    5. 隐私边界变差。

    6. 多端同时使用时容易出现旧数据覆盖新数据。

    修复

    建立：

    
Memory Router

    在不读取完整个人记忆的情况下，只根据当前请求判断：

    
是否可能依赖个人上下文？

    ---

    P0-2：每轮强制上传

    问题

    即使：

    
Memory Before == Memory After

    仍执行写入。

    影响

  • 无意义网络请求
  • 数据库写放大
  • 版本号不断增加
  • Sync Event 爆炸
  • Cache 不断失效
  • 多端产生大量无意义冲突
  • 更严重时可能出现旧状态覆盖新状态

    • 修复

    建立：

    
Memory Change Detector

    只有：

    
meaningful_change == true

    才进入：

    
Persist → Sync → Invalidate

    否则：

    
NO-OP

    P0-3：不同 Memory Module 之间直接互相同步

    错误方向：

    
Codex Memory
     ↕
ChatGPT Memory
     ↕
Claude Memory
     ↕
Cursor Memory

    正确结构：

    
             ┌── Codex

             │

             │
             └── Other AI
                    │
                    ▼
             ┌──────────────┐
             │ Memory Core  │
             └──────────────┘
                    │
          ┌─────────┼─────────┐
          ▼         ▼         ▼
       Storage    Index     Sync

    原则：

    各 AI Adapter 不应该互相同步，只和 Canonical Memory Store 同步。

    P0-4：缺少 Canonical Memory

    必须明确：

    谁才是真正的记忆源？

    不能让：

    
Codex = Source
ChatGPT = Source
Claude = Source

    同时成立。

    必须定义：

    
Canonical Memory

    所有 AI 端：

    
Read → Canonical Memory
Write → Canonical Memory

    本地缓存只是：

    
Cache

    而不是事实源。

    P0-5：并发写入存在竞态

    典型问题：

    
09:00:01 Codex 读取 version=15

09:00:02 Claude 读取 version=15

09:00:03 Codex 修改
version=16

09:00:04 Claude 修改
version=16

    如果没有版本检查，Claude 可能覆盖 Codex 的修改。

    修复

    采用：

    
Optimistic Concurrency Control

    至少保存：

    
memory_id
version
updated_at

    提交时：

    
UPDATE memory
SET ...
WHERE memory_id = ?
AND version = expected_version

    如果：

    
affected_rows == 0

    说明发生冲突，不能直接覆盖。

    P0-6：记忆状态不能只有“存在/不存在”

    建议 Memory 至少拥有：

    
id
user_id
type
content
confidence
source
created_at
updated_at
version
status

    其中 status 至少支持：

    
active
superseded
deleted
pending

    例如：

    
用户以前喜欢 A
↓
A = superseded

用户现在喜欢 B
↓
B = active

    不要简单地做：

    
A → delete
B → insert

    否则历史关系和状态变化难以追踪。

    三、记忆召回准确性

    不能简单采用：

    
semantic search
↓
top-k

    因为不同问题需要不同记忆类别。

    例如：

    “我最近在做什么？”

    和：

    “我喜欢什么颜色？”

    虽然都是个人信息，但属于不同记忆范围。

    建议 Recall 综合：

    
Intent
+
Memory Type
+
Semantic Similarity
+
Recency
+
Confidence
+
Explicitness

    形成：

    
Recall Score

    四、Memory 分类体系

    第一版不要做几十种类型，建议先建立六类。

    L1：Identity

    例如：

    ---

    L2：Preference

    例如：

    
喜欢什么

    ---

    L3：Project

    例如：

    
当前项目

技术栈
长期决策

    ---

    L4：History

    例如：

    
过去做过什么
已经尝试过什么
以前做出的决定

    ---

    L5：Constraint

    这一类非常重要。

    例如：

    
不要联网
不要使用某工具
必须兼容某版本
预算
禁止某种方案

    这类记忆优先级应该很高。

    ---

    L6：Temporary Context

    例如：

    
今天正在调试某个 bug
这轮正在讨论某个文件
当前任务

    这种内容不要直接作为长期 Memory。

    否则记忆库会迅速污染。

    十二、Cache 与失效机制

    推荐：

    
Memory Cache

key:
user_id + memory_id

value:
memory content + version

    读取时：

    
cache.version == store.version

    才认为有效。

    例如：

    
version 15
↓
version 16

    自动：

    
invalidate version 15

    不要单纯依靠 TTL。

    正确：

    
Version-based invalidation
+
TTL fallback

    其中：

  • Version：解决一致性
  • TTL：防止永久脏缓存

    十九、八条最终设计原则

    1. Memory 不再是 Session 的默认上下文

Message
→ Router
→ Recall

    3. Recall 必须是最小集合

    
Relevant Memory

    4. Canonical Store 是唯一事实源

    6. 所有写入必须幂等

    二十、最终修正版：Cross Memory System vNext

    
Memory Access Policy

默认：
NO MEMORY

触发：
Memory Router 判断个人相关性

读取：
按 Scope + Relevance + Confidence + Recency 最小召回

写入：
只有明确新增/修改/删除个人记忆才执行

明确“记住”：
高优先级立即进入 Memory Write Pipeline

持久化：
Canonical Memory Store

并发：
Optimistic Lock + Version

重复请求：
Idempotency Key

同步：
Event-based Sync

缓存：
Version Invalidation + TTL Fallback

异常：
Store / Sync / AI / Network 分离处理

生命周期：
明确 Client / Connection / Worker / Listener / Timer 的创建和释放

默认行为：
无个人关联 → 完全不碰 Memory
