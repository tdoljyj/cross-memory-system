## 1. 产品目标与核心结论

Clued 是用户拥有、可在获授权 AI 之间恢复的个人上下文层。开发 Clued 本身与使用 Clued 应遵循同一连续性原则：已授权保存的信息，不应因切换模型、设备或登录入口而要求用户重复说明。

本方案采用：**一个在线 Canonical Store，多个明确归属的上下文范围，独立的调用授权，以及受控的接受和发布流程。**

必须同时满足：

1. 开发上下文可以独立于 Dogfood 用户界面的登录会话保存。
2. 用户之后登录，可以读取被明确授权的既有开发历史，不以“当时未登录”为排除条件。
3. 读取开发历史不自动获得修改、审批、发布或他人数据访问权限。
4. 普通用户默认消费已发布产品信息，自有上下文仍由用户控制。
5. 内部事实接受与对指定受众发布分别授权。
6. 产品更新不覆盖用户自己的偏好、任务、观察或个人项目事实。
7. 未保存的对话不能凭登录恢复；本地草稿不能冒充已进入 Canonical。

“没有登录 Dogfood”不等于“没有任何有效身份”。Developer 可以使用独立、已授权的开发连接；若所有连接都未认证，只能保存明确标记的本地草稿，不能创建无归属的线上权威记录。

## 2. 与现有 Clued 合同的关系

继续遵守 v1.6：

- 认证的 Clued 服务及其 Supabase 数据层是唯一在线 Canonical Store。
- 用户 Profile、Global、Projects 的个人语义保持不变；Global 不是全体用户共享区。
- Canonical Record、Project、Event、Receipt、Evidence 保留稳定 ID 和各自职责。
- Git、Markdown、Bundle、索引和设备副本是代码材料、受控导出或派生表示，不成为业务反向写入口。
- 正式业务变更使用服务端授权、CAS、幂等与回执，不恢复本地双写。
- 已接受的 Phase2 Naming/Structure 结果按其精确范围继续有效；本方案是后续业务语义设计，不重置固定 21 步。

已安装的 Developer/User Skill 可以继续用于已支持操作。新增上下文共享与发布能力只有实际接口、授权、验收成立后，才可投影到 Skill 中；不能由 Skill 文案提前创造能力。

现有 TM19 工程发布／读取证明只覆盖其受验对象。本文的“产品上下文发布”是新的业务效果，不能直接继承 TM19 的运行验收或权限。

## 3. 实体与所有权模型

| 逻辑概念 | 职责 | 所有权与限制 |
|---|---|---|
| Account / Principal | 认证身份或服务主体 | 身份从可信认证获得；同邮箱、昵称、机器或聊天声明不证明主体相同 |
| Product Identity | Clued 产品稳定标识，关联定义与版本 | 标识不是权限主体；需另指明有权治理该产品的主体 |
| Project | 稳定项目身份 | 使用 canonical_project_id；项目名叫 Clued 不等于产品身份 |
| Context Scope | 指定所有者、项目和用途下的可寻址记录集合 | 是逻辑范围，不强制单独建库或复制全部记录 |
| Developer Context | 开发任务、决定、操作、失败、代码及证据引用 | 归属已验证的项目所有者／治理主体；作者身份不自动等于所有者 |
| Product Governance Context | 指定产品范围的候选、已接受决定、约束与状态 | 每条记录明确效力；存储在 Canonical 不等于产品已经接受 |
| User Context | 某用户的画像、Global 与 Projects | 用户自己的上下文，不是产品治理树的下级 |
| Agent Binding | 某 Agent Host 代表主体调用服务的可撤销委托 | 独立凭据、范围、动作、环境、期限与撤销状态 |
| Context Access Grant | 向指定主体／Binding 授予指定范围的访问 | 不是所有权转移；不因能读就能改或再授权 |
| Project Context Link | 用户项目引用另一个受控 Context | Link 负责关联，Grant 负责访问；有 Link 无 Grant 仍不可读 |
| Dogfood Participation | 用户或其项目参与 Clued 自测的关系 | 可撤销、限定环境；不是 User Instance Type，不必赋予额外权限 |
| Acceptance Decision | 对精确候选和范围产生接受效果 | 需合格签发者、授权依据、版本与证据 |
| Publication | 将已批准的具体内容按受众、渠道和环境提供消费 | 保存不可混淆的内容版本、发布指针、状态及回执 |
| Feedback Submission | 用户主动共享的观察及证据包 | 原观察归属不变；开发方只获得提交范围的使用权 |

“User Instance”仅作某个用户使用 Clued 的描述性术语，不作为独立租户类型或新的事实容器。

单一事实源的准确含义：**同一事实身份只有一个权威变更入口，派生表示保留来源；不同主体与范围可以各自拥有权威记录。**

用户“觉得流程难用”与产品“该流程通过规范验收”可以同时存在，它们描述不同主体和命题，不能互相覆盖。

## 4. 信息流与三条通道

```text
有认证的 Developer Binding
          │ 保存开发状态、任务、决定和证据引用
          ▼
    Developer Context ─────── 授权引用 ──────► 用户的“开发历史”视图
          │                                     ▲
       精确候选                             登录 + Grant + Link
          ▼                                     │
    Acceptance Decision                    普通用户项目
          │                                     │
          ▼                              最小范围反馈提交
 产品范围的权威记录 ◄── 接受 ── 开发候选 ◄── Feedback
          │
   独立 Publication 授权
          ▼
 已发布产品投影 ───── 按受众读取 ─────► 普通用户／Dogfood 用户
```

图中箭头表示数据流，不表示所有权继承。

### 4.1 开发连续性通道

目的：开发者跨会话继续工作。开发记录通过开发委托写入其授权 Context。用户后续通过 Grant 读取既有历史。私有读取无需向全体用户发布。

### 4.2 产品事实接受与发布通道

目的：形成经接受的产品决定，并将其中获批准内容发布给特定受众。不能从开发目录全量复制，也不能把所有 Accepted 记录自动公开。

### 4.3 用户反馈通道

目的：把用户选择共享的观察交给开发分析，最终回告处置结果。反馈不默认批准产品需求，也不默认授予完整私人上下文读取权。

这三条通道可复用同一数据库、事务与接口层，但必须有不同的授权效果和审计类型。

## 5. 不依赖 Dogfood 登录的开发记录保存

### 5.1 开发开始前

服务或适配器确定实际主体、Agent Binding、canonical project、Context 所有者、目标环境和写入授权。连接已可用时复用有效委托，不重复要求用户登录；没有合法委托时不能借用管理员凭据。

Developer Skill 自身没有数据库、登录状态或隐含所有者。安装 Skill 不能作为保存成功的证据。

### 5.2 保存内容

在既有用户授权与采集策略覆盖下，持久化足够恢复工作的结构化上下文：

- 目标、当前状态、已完成动作和支持证据；
- 决定、理由与被否决方案；
- 失败、阻塞、矛盾、撤回结论；
- 精确仓库／Commit／运行／部署目标引用；
- 一项明确的下一步，以及来源、时间、可信程度。

不默认保存全部聊天、凭据、完整代码副本或未经授权的附件。代码正文继续由其代码仓库管理，Clued 保存恢复任务所需的引用与证据元数据。

开发进展的保存不要求产品 Acceptance。只有形成产品范围的正式决定或声明时，才进入相应接受门禁。

### 5.3 在线保存结果

授权写入必须在同一业务事务中提交实体变更、Event 和 Receipt。返回实际 ID、版本及操作结果。请求超时标记 UNKNOWN，以相同幂等键查询／重试，不能再次提交另一份“同样内容”。

会话收尾 checkpoint 记录实际完成、阻塞和下一步；不为已自动产生 Event/Receipt 的变更再次追加重复业务记录。

### 5.4 完全离线或未认证

在用户允许的设备存储中保留 LOCAL_DRAFT，至少包含本地草稿 ID、来源会话、创建时间、内容摘要及拟归属范围。拟归属不代表服务器已确认。

之后接入时，经过真实身份、来源、所有者与导入范围核验，通过受控 Import 提交；旧文档修改不能直接反向覆盖 Canonical。导入保留原 observed_at 与实际 recorded_at，禁止伪造历史回执。

MVP 不提供匿名跨账号“自动认领”。无法证明来源或所有权时保持待确认草稿；若根本未持久保存，不承诺恢复。

## 6. 用户稍后登录时恢复开发历史

### 6.1 目标体验

上午只用 Developer Skill，下午才登录参与 Dogfood 的用户账号：只要上午已授权保存、下午有对应读取授权，用户应能恢复上午的记录，不必重述，也无需上午同时打开用户界面。

### 6.2 服务端恢复流程

1. 认证 User Binding，取得真实主体；登录只证明身份，不推导任意开发权限。
2. 获取该主体当前允许发现的项目／Context 摘要；未授权资源名称、计数和存在性也不泄漏。
3. 解析用户项目的 Project Context Link，读取对应有效 Grant。
4. 检查主体、Binding、动作、scope、环境、历史范围、字段与附件范围，以及撤销状态。
5. 按授权构造上下文包，保留 canonical IDs、来源版本、候选／有效／历史标记和最近核验时间。
6. 页面展示可访问的开发历史入口；向 AI 注入时仍按当前任务相关性选择最小范围，不全量灌入历史。
7. 返回可见记录、缺失／过期／不可用原因与分页游标；访问审计遵循敏感度策略，不记录无关正文。

### 6.3 历史授权策略

Grant 必须显式规定 history_policy，不能把授权签发时间当作唯一历史分界：

| 策略 | 含义 |
|---|---|
| EXISTING_ONLY | 读取签发时服务器冻结读点内允许的既有记录，不自动包含后续新增 |
| EXISTING_AND_FUTURE | 读取该范围内既有及后续获准内容；需明确长期授权意图 |
| SINCE_CURSOR | 从服务器确定的提交游标／读点开始，不依赖可修改的客户端时间 |
| EXPLICIT_SET | 仅指定记录、版本或发布对象 |

读取既有记录的最新修订，还是绑定时的固定版本，也要独立指定 version_policy。任何策略都不能越过当前撤销、保密和保留限制；历史访问权不等于已删除／被拒绝材料的恢复权。

自己的开发项目，首次连接时推荐选择 EXISTING_AND_FUTURE 的只读授权，明确包含现有记录及后续记录。用户确认一次后在有效期与范围内持续生效；不对每条历史重复提问。其他所有者的项目必须由该项目有权主体授予，不能靠同名或“也是我的账号”自动归属。

### 6.4 结果矩阵

| 条件 | 登录后的行为 |
|---|---|
| 已保存，既有 Grant 包含历史 | 直接提供授权入口与按需恢复 |
| 已保存，Grant 只覆盖签发之后 | 不显示更早内容；允许发起扩大历史范围的明确申请 |
| 已保存但无 Grant | 不可读取；有权主体完成连接／授权后再恢复 |
| 已保存到其他主体拥有的开发项目 | 需要该所有者或被委托者授权，不能自动迁移所有权 |
| 只有 LOCAL_DRAFT | 通过受控导入确认后才成为线上记录 |
| 只存在另一 AI 私有对话且无导出渠道 | 登录无法恢复，不声称已捕获 |
| Grant 已撤销 | 后续读取拒绝，处理受控缓存失效 |

### 6.5 引用，不重复建一份权威正文

历史恢复默认通过 Link 引用同一记录。用户添加个人批注时，创建归属该用户的 Annotation／Record 并引用来源。源记录变化不重写用户批注；源不可用时引用显示失效或受限，而不是静默保留为当前权威。

需要离线阅读时使用标明来源版本和授权范围的只读投影。转换、脱敏或总结不是原事实的隐形副本，必须标出派生性质。

## 7. Dogfood 与普通用户测试边界

Dogfood 是参与关系，Role 是职责集合，Entitlement 是参与资格，Capability 是具体动作权。三者不互为别名。

Dogfood Participation 至少关联用户／项目、产品、目标环境、参与状态和适用期限；额外预览能力通过单独 Grant 提供。开发者可以参与，后续其他获授权测试者也可参与，不改变普通用户类型。

提供两种可辨识工作模式：

| 模式 | AI 可用上下文 | 用途 |
|---|---|---|
| 普通用户自测（默认） | 该用户自有上下文、正式发布信息与明确预览授权 | 验证普通用户路径 |
| 查看开发历史 | 额外加载用户主动选定且已获授权的开发 Context | 继续开发、复盘和定位问题 |

模式名称不授予权限，服务仍逐次验证 Binding 和 Grant。历史阅读只扩大明示的读取上下文，不增加开发写入或发布权限。

同一 AI 会话若已经读过内部开发材料，切换页面或撤销 Token 不能让模型“忘记”。需要证明普通用户视角时，新建隔离的模型上下文／会话，只注入普通用户允许的信息，并使用 User Binding。工具凭据隔离与模型输入隔离都必须验证。

退出 Dogfood 参与和撤销开发历史 Grant 是两个动作。系统须展示具体被撤销的关系；不因停止自测删除用户项目或开发历史。

## 8. 访问与委托合同

授权判断必须同时满足：可信主体、有效 Binding、允许动作、有效资源 Grant、精确资源与环境、当前有效期及撤销状态、字段／证据策略。角色策略内部可以有明确的允许规则，但最终约束不能因账号兼任角色而被绕过。

| 动作 | User Binding | Developer Binding | Acceptor 委托 | Publisher 委托 |
|---|---|---|---|---|
| 自有用户 Context 读写 | 按用户授权 | 不自动获得 | 不自动获得 | 不自动获得 |
| 读 Developer Context | 仅有明确只读 Grant 时 | 按指定开发范围 | 仅审查所需范围 | 仅发布所需范围 |
| 写 Developer Context | 默认不允许 | 按开发授权 | 不自动获得 | 不自动获得 |
| 提交产品候选 | 按单独能力；反馈不等于候选批准 | 按指定范围 | 可按授权 | 不自动获得 |
| 接受候选 | 不自动获得 | 不自动获得 | 指定对象及范围 | 不自动获得 |
| 发布／撤回发布 | 不自动获得 | 不自动获得 | 不自动获得 | 指定受众、环境和内容 |
| 修改 Grant | 所有者或有效授权委托 | 仅明确有 grant 管理权时 | 不自动获得 | 不自动获得 |

Acceptor 与 Publisher 是授权职责，不要求不同自然人或独立账号；同人签发时保留两种动作和依据。某些高风险类型是否需要独立复核由相应策略规定，不一律引入多人审批。

Scope 以已验证主体和服务端资源关系判定；不信任调用方传入的 owner 字段。Grant 不可转授，除非明确包含可转授权及边界。删除 Link 不一定撤销 Grant；界面须区分“移除入口”和“撤销访问”。

Supabase/PostgreSQL 执行要求：最小 GRANT、RLS 与受限服务入口共同生效。普通请求保留最终用户／Binding 身份；不能让所有请求共用 service_role，再靠 Skill 判断权限。service_role、BYPASSRLS、表所有者及高权限函数／视图路径逐一纳入审查。默认 permissive RLS 多条策略按 OR 组合，不等价于本合同的多约束共同满足。[Supabase RLS](https://supabase.com/docs/guides/database/postgres/row-level-security)、[PostgreSQL 行安全](https://www.postgresql.org/docs/current/ddl-rowsecurity.html)

附件、搜索、分页、计数、导出、RPC、后台任务与索引必须遵守等价范围过滤，不能只验证详情页。缓存键绑定实际 scope、策略版本、可见字段与相关授权版本，避免跨用户或跨模式缓存复用。

## 9. 事实登记与正式接受

Canonical Store 里的记录可处于 candidate。它权威地记录“谁提出了什么”，但不保证该主张为真或产品已接受。

Acceptance 流程：候选与证据提交 → 类型与范围检查 → 有权主体审查 → CAS 检查 → 接受／拒绝决定及 Event/Receipt 原子提交。

接受对象包括 Requirement、Decision、Contract 或经证据支持的 State；按已有类型映射，不把整个开发目录作为一项接受对象。

接受决定至少绑定：candidate ID/version/hash、精确命题、owner/scope、适用产品版本与环境、证据版本、签发主体与实际 Binding、授权依据、接受及排除范围、前任关系、时间、未关闭义务和结果。

“设计已接受”“代码已实现”“验证通过”“部署成功”“对用户开放”是不同命题，需要不同证据。任何一项不得自动代替其余项。

仅改变展示位置或增加同范围引用时，沿用原 canonical ID。开发观察经分析形成新的产品决定时，创建新命题的 Record，关联 derived_from／evidence，不将私有源记录原地搬到产品共享范围，也不销毁原观察。

## 10. 发布合同与可靠交付

### 10.1 发布不是自动公开

Publication 明确 audience、channel、environment、product/release 和字段范围。受众可以是本人、指定参与者、测试组、全部认证用户或公开访问；默认不扩大受众。

“内部已接受”仍可以保密。“预览信息已发布”不表示正式生产可用。历史发布记录不因部署版本变化而被重写。

### 10.2 发布授权绑定

发布清单至少包含：

- source record IDs、版本和内容哈希；
- 接受决定及授权依据；
- publisher 主体与 Binding；
- 目标产品／发布版本／环境／受众／渠道；
- classification、字段白名单、脱敏策略版本；
- 投影器版本、生成参数、最终 payload hash；
- candidate ID、前任 publication、expected-current CAS；
- 幂等键、request hash、有效时间与失效条件；
- 结果 Event/Receipt、交付状态和核验引用。

最终可见字节须与批准对象绑定。源正文、受众、环境、脱敏策略或最终投影变化，必须重新检查并取得覆盖新内容的批准；不得用旧摘要、旧 PASS 或同名文件替代。

### 10.3 生成与事务

1. 在固定来源读点生成可审核发布候选，凭据扫描与授权检查通过后计算摘要。
2. 若 AI 生成摘要，先把具体摘要冻结为候选供审查；模型再次生成的不同文本不能自动视为同一确定性投影。
3. 提交发布事务时重新验证权限、来源版本、批准绑定和 expected-current。
4. 数据库原子提交 Publication 意图、Event、Receipt 与待交付任务。事务回执表示意图已提交，不表示外部交付已完成。
5. 消费者以幂等任务将内容写入不可变版本位置，核对内容后再切换受控 current 指针。发布消费者若不支持不可见暂存与安全切换，则不能承载要求原子可见的渠道。
6. 全部 required consumers 完成指定内容核验后记录 DELIVERED／VERIFIED；失败保留上一有效版本，并明确 PENDING／FAILED／UNKNOWN。

不得宣称跨数据库、CDN 与设备形成一个 ACID 事务。使用数据库事务加可恢复交付记录／outbox；MVP 允许人工触发重试，不要求新消息平台。权限或批准在交付前撤销时取消后续交付；已可见部分进入撤回处理。

每个 current 指针按产品、渠道、环境和受众边界定义，不能只有一个全局“最新版”。回滚是有授权的新指针操作及新回执，不能改写既有发布历史。

### 10.4 隐私与内容投影

发布 payload 不携带用户原始私有记录、凭据或无需公开的来源路径。公开投影中的来源使用可公开引用或不透明标识；完整证据通过受保护审计路径读取。

相同事实的多个渠道表示保留同一来源版本。确实形成新的摘要命题或产品决定时明确其新 ID 与推导来源，而不是把重新编写的正文冒充原记录。

## 11. 用户观察与反馈闭环

用户观察首先保存在其授权 User Context。共享动作创建一个明确范围的 Feedback Submission，绑定观察版本、允许共享的字段与附件、开发接收范围、用途和必要的后续联系权限。

完整流程：

```text
用户观察
  → 选择共享材料
  → Feedback Submission 与提交回执
  → 开发分流：待分析／重复／需补证／无法复现／候选需求
  → 产品 Acceptance
  → 实施与验证证据
  → 产品 Publication
  → 向反馈者提供获准的处理结果
```

没有成为产品需求的反馈也可以以明确理由关闭。反馈结果使用受控状态视图；MVP 通过用户主动查询提供，不因有反馈关系自动给用户发送站外消息。

原观察与开发工单使用关系链接。反馈的接收副本是按共享授权冻结的证据包，保留源 ID/version 与变换信息；不能冒充第二份可独立修改的源观察。

分享授权变更必须检查相关 evidence、索引、导出、开发接收范围与后续引用。用户撤回共享与开发方记录“曾收到反馈”是不同保留问题；允许保留的最小审计记录不应包含已要求删除的原始敏感正文。

已基于反馈独立验证的产品缺陷事实，可以在移除用户可识别资料后保留其独立证据；若结论只依赖不可再用的材料，标记需复核，不静默保持为已验证。

反馈和证据中的指令均作为数据处理。它们不能触发工具授权、候选接受、发布或读取其他用户信息。

## 12. 生命周期、版本与新鲜度

以下为独立逻辑维度，实现时映射到现有状态与类型，不能破坏旧客户端枚举合同。

| 维度 | 示例状态 | 核心含义 |
|---|---|---|
| 采集／持久化 | LOCAL_DRAFT、COMMITTED、UNKNOWN | 是否确实进入服务 |
| 审批 | DRAFT、PENDING、ACCEPTED、REJECTED | 候选是否被有权主体接受 |
| 事实效力 | ACTIVE、SUPERSEDED、REVOKED | 命题当前是否适用 |
| 发布可见性 | UNPUBLISHED、PUBLISHED、WITHDRAWN | 是否允许通过该 Publication 消费 |
| 交付状态 | PENDING、DELIVERED、VERIFIED、FAILED、UNKNOWN | 指定消费者实际收到并验证了什么 |
| Grant | ACTIVE、EXPIRED、REVOKED | 调用是否仍获授权 |
| 新鲜度 | CURRENT、STALE、HISTORICAL、UNKNOWN | 是否足以作为本次当前状态依据 |

有效转换：

- ACTIVE 可直接 REVOKED，说明判错原因和证据；无需先造一个替代事实。
- 被更精确命题替代时标记 SUPERSEDED，保留双向关系与生效区间；旧记录仍可用于获授权历史审计。
- Publication 可撤回而源事实仍 ACTIVE，例如收窄受众或纠正错误脱敏。
- 拒绝一个候选不删除它曾被提出的证据。
- 已撤回内容不得借“回滚”自动再次发布，必须重新检查当前权限与理由。

时间字段至少区分 observed_at、recorded_at、valid_from/valid_until、last_verified_at 和授权期限。授权历史范围使用可信服务读点或不可变版本集合，不以客户端补写的 observed_at 控制访问。

版本轴分别保留实体 CAS version、Canonical 读点、snapshot version、产品 release、文档版本、授权策略版本和投影器版本；不同轴不得比较大小或互相替代。

“某日发布过版本 X”是历史事件；“当前运行 X”是对具体目标的可变断言。后者过期须复核或降级，不把 TTL 到期解释为前者变假。

## 13. 撤回、失效与离线边界

### 13.1 四种不同操作

| 操作 | 改变什么 | 后续处理 |
|---|---|---|
| 事实纠正／撤销 | 命题效力 | 标记替代或撤销，检查依赖该命题的发布与决定 |
| 发布撤回 | 指定受众的可见渠道 | 关闭 current 可见入口、失效受控缓存、记录交付处置 |
| 授权撤销 | 主体／Binding 的未来访问 | 拒绝后续请求，取消未完成任务，隔离账号相关缓存 |
| 数据删除 | 按所有者请求及保留政策清除数据 | 覆盖服务、附件、索引、导出及备份处置，保留允许的最小审计 |

四者使用不同操作类型与 Receipt，不用一个 revoked 字段替代全部效果。

### 13.2 最低执行规则

敏感读取以及所有写入、接受、发布、Grant 修改，执行时检查当前服务端授权状态。授权撤销提交之后启动的这些请求不得继续利用旧 Token 或旧允许缓存。并发请求以其已验证读点／事务顺序解释；不能保证收回撤销前已经返回的数据。

访问 Token 验签只是认证的一部分。当前授权状态由服务验证；若所选调用链无法判断当前 Grant 或 Binding 是否撤销，敏感操作拒绝，不能借尚未到期 Token 判为允许。

受控客户端记录 publication/version、来源集合、策略版本、scope、同步游标与授权有效性。重连必须先处理撤销／失效，再恢复读写；账号切换清除或隔离前一账号的上下文包和缓存。

默认不离线缓存开发内部正文、敏感附件、权限状态或发布授权。需要离线能力时必须另有明确 Grant 与有效期；到期后不继续执行敏感操作。已存在的 LKG／缓存策略按其版本复用，不能由本文擅自扩大。

公开且不可变的历史发布可以保留历史副本，但不能仅靠该副本断言当前产品能力。用户私有离线 Bundle 同样保持只读与来源标记。

### 13.3 撤回依赖与局限

至少追踪直接的 source version → acceptance → publication → required consumer 依赖；复杂传递依赖可按需计算，不要求记录每次模型推理。

来源撤销后，服务在消费时拒绝依赖该无效来源的当前发布，或根据独立证据重新接受新的来源绑定；后台未完成重建不构成继续提供错误当前状态的理由。历史审计保留适用说明。

对受控消费者记录失效游标与确认，对未确认者报告待处理。对已经下载、截图、复制或进入第三方模型的内容，不能承诺远程清除；记录授权与披露边界，并阻止后续受控读取。重新开始普通用户测试时使用新的隔离上下文。

备份保留及删除期限由正式保留政策配置并在发布前核验；审计可追踪不等于敏感原文永久保留，也不等于立即物理抹除所有备份。

## 14. 逻辑数据合同

此节定义必须表达的信息，不要求一合同一表。最小实现可复用现有 Record/Evidence/Event/Receipt，并用受控关系或类型化扩展承载新概念。

### 14.1 ContextRecordEnvelope

| 字段组 | 最小内容 |
|---|---|
| 身份 | canonical ID、record type、entity version |
| 归属 | 可信 owner_ref、context scope、可选 canonical_project_id、subject_ref |
| 内容与效力 | 正文或受保护引用、classification、来源可信类别、生命周期与适用范围 |
| 时间 | observed_at、recorded_at、有效区间、last_verified_at |
| 来源 | actor principal、Binding、证据 IDs/versions、操作／会话引用 |
| 关系 | derived_from、supersedes、annotation_of、关联决定／发布 |
| 审计 | Event/Receipt 引用，原始 source hash |

缺字段不能填造历史值。导入旧资料缺少回执或身份时明确 provenance_incomplete，保持候选或历史状态。

### 14.2 AccessGrantEnvelope

必须包含 grant ID/version、grantor 及授权依据、grantee principal／Binding selector、resource/context selector、actions、环境、history_policy、version_policy、可信历史游标或固定集合、字段／附件允许范围、用途约束、有效期、撤销版本与可否转授。

Grantor 不得授予超出自己可授范围的权利。客户端声明的“用途”不能独立作为安全依据；以实际 Binding、资源与动作策略约束。Grant 调整按 CAS 提交，扩权单独授权，缩权触发缓存失效。

### 14.3 ProjectContextLink

包含 link ID/version、source context、destination user project、grant reference、用途及展示名称。Link 不承载凭据、源正文或独立权限。目标项目的写权限不能通过 Link 反向写源。

### 14.4 Acceptance / Publication / Feedback

Acceptance 采用第 9 节的精确候选与授权绑定。Publication 采用第 10 节的内容、受众、环境、生成和交付清单。Feedback 采用第 11 节的选择共享与观察来源合同。

三者共用变更基底：operation ID、actor/Binding、request hash、幂等键、CAS base、target ID/version、policy version、结果、Event/Receipt 及实际提交时间。

幂等键作用域必须包括主体及操作边界。同键同请求重放原结果；同键不同 request hash 拒绝。不同主体不能通过猜测幂等键读取他人的结果。幂等重放也要重新检查当前读取结果的资格，不能用旧 Receipt 绕过撤销。

### 14.5 ContextPackage

恢复给 AI 的包包含：当前主体与目标范围的不透明引用、来源 ID/version、selection policy、生成时间、新鲜度、项目状态／任务／决定、完成／失败／阻塞、下一步，以及不可用项说明。

包是按需派生结果，不是新权威源。包中引用的开发日志、反馈和第三方文本均为数据；授权合同由可信服务单独提供，不能混入任意正文让模型自行选择权限。

## 15. 操作合同与错误行为

下列名称仅标识所需业务能力，不宣称已存在对应端点。正式开发前逐项映射服务真实 advertised schemas。

| 逻辑操作 | 前置条件 | 成功产物 |
|---|---|---|
| 保存开发 checkpoint | 已验证开发 Binding、明确 owner/scope、写授权、CAS | 原子状态／事件／回执 |
| 导入本地草稿 | 认证、来源与归属核验、用户覆盖导入的授权 | 可追溯导入实体及 Receipt |
| 创建／修改 Grant | 授权管理资格、资源范围、CAS | Grant 与审计结果 |
| 建立 Project Link | 目标用户项目可写、有效或可验证待激活 Grant | Link，不隐含扩权 |
| 恢复历史上下文 | User Binding、当前 Grant、历史和版本策略 | 来源绑定的 ContextPackage |
| 提交／接受候选 | 类型校验及相应动作授权 | candidate 或 Acceptance Decision |
| 发布／查询交付 | 精确批准、Publisher 权限、CAS | 发布意图回执及独立交付状态 |
| 撤回／撤销 | 相应权限、精确对象、影响范围 | 失效状态、Event/Receipt 和处理清单 |
| 提交／查询反馈 | 明确共享范围／反馈关系授权 | Submission／受限处理视图 |

必须区分 UNAUTHENTICATED、FORBIDDEN、NOT_AVAILABLE、STALE、CONFLICT、PENDING、FAILED、UNKNOWN。对未经授权主体可以统一返回不透露存在性的 NOT_AVAILABLE；受保护审计仍记录真实拒绝原因。

CAS 冲突返回重新读取与语义合并要求，不自动覆盖。外部写入结果未知时先按 operation ID／幂等键核查，不以超时推断失败并重新发起另一笔操作。

授权失效、源不可用、环境错绑、签名或策略版本不匹配时只阻断相关读取／写入／发布，不删除项目或污染其他范围。

## 16. 用户交互与 Skill 分工

### 16.1 用户界面表达

使用普通语言解释具体效果，不要求用户理解内部合同名：

- 连接：“连接这个项目的开发记录。”
- 只读历史：“允许查看已有记录和以后新增的记录；不会获得修改或发布权限。”
- 保存：“已保存”，附可查记录；不确定时：“保存结果待确认。”
- 未连接：“尚未连接开发记录。”不能把无权限表现为内容已丢失。
- 模式：“普通用户自测”与“查看开发历史”。
- 撤销：“停止之后访问；已经导出的内容可能仍有副本。”
- 过期：“这是历史记录，当前状态尚未核验。”

已存在有效 Grant 时直接使用，不重复授权。首次创建 Grant、扩大资源／历史／动作范围等实际新增权限，使用具体可审阅的授权内容。

### 16.2 Developer Skill

读取实际开发连接、支持的合同与范围；恢复最小开发工作状态；按现有授权保存操作与 checkpoint；提交候选或在实际 Publisher 委托下执行发布。没有对应能力时报告缺失，不创建替代本地权威记忆。

### 16.3 User Skill

恢复用户自有上下文与已授权项目；提供已发布产品信息；经明确选择读取开发历史；提交授权反馈；展示实际保存回执和失败状态。默认不使用 Developer 凭据，也不从安装状态推断权限。

### 16.4 多 Host 与上下文隔离

每个 Host 独立 Binding，撤销一台设备不应误删其他设备的数据。新会话从服务恢复，不依赖另一平台的聊天记录或私有 Library。普通用户无须 GitHub 访问。

Skill 的静态文档只保存路由、可用机制和边界，动态事实通过服务读取；长期正文不复制进 Skill。MCP 不可用时只用实际支持且获授权的 JSON API，不根据猜测拼造 mutation。

## 17. 与现有架构的映射与变更影响

| 本方案内容 | 优先复用 | 必须新增或核实的合同 | 对既有治理的影响 |
|---|---|---|---|
| 开发工作状态保存 | Record/Project/Event/Receipt、checkpoint | 与 Dogfood 会话独立的主体和 owner 绑定 | 不改个人 Global 含义；核实真实工具支持 |
| 私有开发历史读取 | 既有 scoped read、稳定项目 ID | Context Grant、Link、可信历史与版本策略 | 如新增 role/scope/consumer，登记后继合同 |
| Dogfood 参与 | 普通用户账户与项目 | Participation、测试环境、模型上下文隔离 | 不引入新用户类型 |
| 产品事实接受 | Decision、Evidence、CAS | 类型化接受范围与 Acceptor 委托 | 新业务语义，不自动继承结构接受 |
| 产品上下文发布 | 确定性生成、版本化 artifact、Receipt | audience、publication pointer、交付状态与撤回 | 与 TM19 工程发布分清；新消费者单独验收 |
| 反馈共享 | 用户观察、Evidence、关系引用 | 最小共享范围、接收使用权、处理回告 | 不扩大 Developer 的私人数据权限 |
| 撤回与删除 | 已有生命周期、审计、保留策略 | 派生依赖、当前授权检查、受控缓存失效 | 受影响索引／导出／备份纳入验证 |
| Skill 适配 | 已安装薄 Developer/User Skill | 新能力的实际 schema 与 fail-closed 行为 | 后续更新，不宣称原 Skill 不存在 |

本方案不宣称上述扩展满足 semantic no-change。正式修改受冻结 namespace、Registry、Manifest、权限、版本轴或消费者义务时，先登记精确后继 subject、变更理由、影响表和受影响证据，再按既有失效规则重验。

未受影响的历史接受结果继续有效，不因一个新功能无条件重跑整个 Phase2，也不以旧 Gate PASS 代替新业务测试。

## 18. 分阶段实施顺序

以下 A–F 是本方案后续实施阶段，不替代或重排既有 Phase2 的 21 步。本文编制完成不表示 A–F 已执行。

| 阶段 | 工作范围 | 交付与出口条件 |
|---|---|---|
| A：合同与影响接受 | 精确受审对象、现有能力映射、所有权、Grant、历史、接受／发布与消费者合同 | 受影响后继 subject、命名／权限映射、测试输入及明确接受决定；未知能力不写成存在 |
| B：开发保存与晚登录恢复 | 独立开发 Binding 保存，用户历史只读 Link，相关性恢复与隔离自测 | 两个独立 Binding 的真实“先开发后登录”恢复通过；普通用户不能写开发区 |
| C：产品接受与发布 | 精确候选、两种授权效果、内容冻结、CAS、交付状态 | 未接受／未发布内容不对普通用户暴露；修改源后旧批准拒绝；故障恢复通过 |
| D：反馈与撤回闭环 | 最小共享、处理回告、来源失效、Binding 撤销、受控缓存处理 | 反馈不会自动成为产品决定；撤回后新访问拒绝；不假报外部副本清除 |
| E：真实消费者与 Skill 更新 | 受验接口映射、前端、MCP/实际 API、恢复、索引、附件与导出 | 真实运行路径的允许与拒绝证据；技能只声明已支持能力 |
| F：限定发布与观察 | 使用实际受权测试账号逐批启用、发布记录、失败监测与回退 | exact release/环境/受众绑定，核心端到端验收通过，限定能力发布声明 |

B 阶段可作为独立价值交付，不必等待完整产品广播功能；它必须具备自己的授权、审计与撤销基础，不能把必要隔离推迟到 D。

C 阶段允许首次只发布到一个受控渠道。未支持撤回或无法隔离受众的外部渠道保持关闭；D 补齐完整派生处置后再扩大渠道。

MVP 不强制新增团队工作区、组织权限平台、语义自动提升、图数据库、独立消息系统或全聊天采集。跨所有者组织级共享先保持关闭；任何范围扩展通过明确后继合同实现。

若存量 Grant 能表达本方案语义，直接复用并验收；不能表达时使用受限扩展，而非改写既有 user_id 归属模型来凑合共享。

## 21. 本次设计决策与证据边界

### 21.1 本候选采用的决策

1. 独立开发持久化，不要求并行登录 Dogfood。
2. 晚登录历史恢复通过 Grant + Link，登录本身不创造访问权。
3. 自有项目推荐明确的“既有及未来记录，只读”长期授权；跨所有者默认拒绝。
4. 普通用户自测默认不加载开发历史，主动查看历史单独标记。
5. 事实登记、产品接受、对受众发布是三个不同效果。
6. 产品与用户上下文分属明确所有者，不重解释个人 Global。
7. 同一权威记录通过引用消费，保留版本和派生来源。
8. 复用现有 Record/Event/Receipt、CAS 和幂等；新增合同按现有治理登记。
9. 开发者、接受者、发布者可由同一人承担，但凭据与每次授权效果不能混同。
10. 撤回有明确在线强制及外部副本边界，不承诺模型遗忘。

这些是按本次要求编制的设计选择，不是自动写入用户 Canonical 的正式接受决定。
