# Clued 两级五视图、单一数据源执行计划

- 版本：v1.0（待确认）
- 日期：2026-08-23
- 状态：仅执行计划，尚未授权实施
- 适用范围：Clued 的状态、待办、决策、归档、日志，以及项目生命周期能力

## 1. 结论先行

Clued 采用“**两级五视图、底层一份数据**”结构：

- 两级：全局级、项目级。
- 五视图：状态、待办、决策、归档、日志。
- 一份数据：同一条状态、任务、决策、归档快照或事件只保存一次；全局和项目只是不同查询视图，不互相复制正文。
- 全局负责跨项目控制、汇总与索引；项目负责单项目详情。
- 日志只记录发生过什么和证据，不再承担当前状态、下一步、优先级或有效决策的权威职责。
- Clued Cloud / Supabase 是 Canonical Source of Truth；Markdown 是可读镜像、导出或迁移输入，不是第二套事实源。

本计划不把“五视图”直接等同于十张物理表，也不预设必须新增哪些数据库表。先定义逻辑实体与读写规则，再映射到现有 Memory CRUD、项目生命周期表和审计能力。

## 2. 目标与非目标

### 2.1 目标

1. 消除全局与项目内容重复、互相覆盖、职责不清的问题。
2. 让任意信息都有唯一权威记录、稳定 ID、明确作用域和可追溯来源。
3. 保留全局总览能力，同时让项目详情完整、独立、可过滤。
4. 保留历史证据，但避免用日志反推当前事实。
5. 兼容已有项目发现、确认、别名、合并、忽略、恢复及审计能力。
6. 支持 Restore → Execute → Commit → Resume 的连续工作流程。
7. 为后续 API、MCP、UI、Skill 和 Markdown 镜像提供同一份语义合同。

### 2.2 非目标

本轮计划不授权以下动作：

- 不合并任何分支到 `main`。
- 不执行数据库迁移。
- 不部署 Worker，不修改 DNS，不把 ChatGPT Sites 当作正式生产入口。
- 不删除旧 Markdown、旧记录或错误草稿分支。
- 不 push、不建 PR、不打 tag、不发布 release。
- 不扩展为完整产品发布；产品化仍受独立发布门禁约束。

## 3. 最终信息架构

| 视图 | 全局级职责 | 项目级职责 | 唯一记录原则 |
|---|---|---|---|
| 状态 | 项目注册表、跨项目优先级、阻塞与健康摘要 | 当前阶段、进展、阻塞、唯一下一步、更新时间 | 项目详细状态只存一次；全局摘要由它派生 |
| 待办 | 全局事项、各项目当前重点、跨项目排序 | 项目任务队列与任务状态 | 任务只存一次；全局视图筛选或聚合项目任务 |
| 决策 | 跨项目规则、产品级或组织级决策 | 仅影响该项目的决策 | 决策正文只存一次；总表引用决策 ID |
| 归档 | 已结束项目/阶段的索引和摘要 | 该项目被替代方案、结束阶段及关闭总结 | 归档是压缩快照，不是日志副本 |
| 日志 | 全局事件流或全部事件查询 | 按 `project_id` 过滤后的项目事件流 | 事件只写一次，不进行全局、项目双写 |

### 3.1 作用域规则

每条权威记录至少具有：

```yaml
id: stable-record-id
user_id: owner-id
scope: global | project
project_id: null | stable-project-id
record_type: state | task | decision | archive_snapshot | event
status: type-specific-status
source_ref: source-or-evidence-reference
version: optimistic-version
created_at: timestamp
updated_at: timestamp
archived_at: timestamp-or-null
```

约束：

- `scope=global` 时，`project_id=null`。
- `scope=project` 时，必须有有效且稳定的 `project_id`。
- 项目改名只修改显示名或别名，不修改 `project_id`。
- 总表只保存索引字段、排序字段和必要摘要，不复制项目正文。
- 未确认的项目只进入“项目提及/候选”流程，不创建五视图或正式项目记忆。
- 每个项目、成员、记录的查询都必须经过授权、最小范围和跨项目隔离检查。

### 3.2 五类信息的权威边界

| 信息问题 | 权威来源 | 不得作为权威来源 |
|---|---|---|
| 现在做到哪里 | 项目状态 | 项目日志中的最近一段文字 |
| 下一步做什么 | 项目状态的唯一下一步 + 有效待办 | 日志、归档、已关闭任务 |
| 为什么这样做 | 当前有效决策及理由 | 状态摘要、聊天中的临时意见 |
| 哪些事要做 | 有效任务记录 | 日志中的动作描述 |
| 以前发生过什么 | 事件日志和证据 | 当前状态覆盖历史 |
| 哪些内容已结束 | 归档快照及关闭原因 | 简单把旧日志移入归档 |

## 4. 写入与读取合同

### 4.1 写入原则

1. 一次用户动作只创建或修改一条权威记录，禁止“全局写一份、项目再写一份”。
2. 需要产生审计证据时，在同一事务中写权威变更和事件记录。
3. 状态切换、任务完成、决策替代、项目合并必须使用版本号或等价并发控制。
4. 原记录不静默覆盖关键历史：决策用 supersedes/replaced_by，任务用状态迁移，归档用快照。
5. 跨多个实体的更新要么全部成功，要么全部回滚。

### 4.2 读取原则

- 全局状态 = 项目注册表 + 每个项目当前状态摘要 + 全局级状态。
- 全局待办 = 全局任务 + 各项目符合展示条件的任务；默认每个项目只展示 Now/最高优先级。
- 全局决策 = `scope=global` 的有效决策 + 项目决策索引；项目正文按需展开。
- 全局归档 = 已关闭项目/阶段/方案的索引。
- 全局日志 = 统一事件流的跨项目查询。
- 项目五视图 = 同一数据集按稳定 `project_id` 过滤。

### 4.3 默认查询顺序

回答“现在在做什么/下一步是什么”时：

1. 读取全局项目注册表与优先级。
2. 读取目标项目状态、有效待办、有效决策。
3. 仅在需要证明、排错或恢复历史时读取日志。
4. 仅在需要查已关闭内容时读取归档。

## 5. 执行阶段与门禁

### 阶段 0：冻结错误方案并建立干净基线

目的：防止未确认结构被误合并或误部署。

任务：

- 将 `fix/memory-authority-cleanup` 标记为 **DO NOT MERGE**。
- 只做差异审计，提取可复用的测试或文字；不直接继承其结构判断。
- 该分支仅在用户明确批准后删除；本计划不执行删除。
- 核对 `feature/clued-project-lifecycle-v1@554729aa` 的实际 HEAD、与最新 `main` 的差异及测试状态。
- 将现有项目生命周期能力作为输入：`clued_projects`、`clued_project_mentions`、项目观察/列表/更新工具、项目 API、别名、去重、确认、忽略、恢复、合并、幂等、并发、RLS 与审计。
- 清点本地未提交的 Clued Continuity Skill 变化；实际实施前恢复到权威基线，最终规则确认后再重新修改，避免错误草稿固化。
- 记录生产基线，但不触碰生产。

门禁 G0：

- `main`、生产数据库、Worker、DNS 均零改动。
- 错误分支与可复用内容清单完成。
- 项目生命周期分支和 Memory CRUD 的真实差异已核验。

### 阶段 1：先写语义合同和 ADR

目的：在改代码、表结构或 Skill 之前，把“不重复”和“谁说了算”写成可测试规则。

交付：

- 《两级五视图语义合同》ADR。
- 五类实体的字段、状态机、作用域约束和生命周期。
- 全局/项目查询规则。
- 项目确认、改名、合并、忽略、恢复时的数据处理规则。
- 决策替代、任务完成、阶段关闭、归档生成规则。
- 权限、RLS、跨项目隔离和审计要求。
- 冲突处理及恢复规则。

必须在 ADR 中明确的决策：

1. 项目状态是独立实体，还是 `clued_projects` 的版本化状态字段。
2. 任务、决策、归档快照、事件分别复用现有 Memory CRUD 到什么程度。
3. “每项目一个 Now”是硬约束还是全局视图默认展示规则；建议采用后者，避免限制真实任务模型。
4. Markdown 镜像是只读导出、双向导入，还是仅迁移期兼容；建议长期以只读导出为主。
5. 归档快照的触发点、保留期和恢复方式。

门禁 G1：

- 每一类信息有且只有一个权威来源。
- 每条全局视图都能说明其来源查询，不依赖正文复制。
- ADR 经过用户确认后，才能进入实现。

### 阶段 2：映射现有实现，确定最小数据变更

目的：尽量复用已完成能力，避免再造第二套项目和记忆系统。

任务：

- 对照最新 `main` 的 Memory CRUD 与项目生命周期分支，形成实体映射表。
- 标注：直接复用、补字段、补索引、补约束、确需新增实体。
- 先设计逻辑实体，再决定物理表；禁止为了“五视图”直接创建十张表。
- 为每项 schema 变更给出向前迁移、兼容读取和回滚方案。
- 评估 RLS、审计、版本冲突和项目合并对历史记录的影响。
- 从最新 `main` 新建后续集成分支，再以保留历史的方式合入项目生命周期分支；不 rebase、不 force push、不 amend/squash 现有提交。

门禁 G2：

- 数据模型评审通过。
- 证明同一记录不会因全局/项目视图产生重复物理写入。
- 所有数据库变化可先以 additive 方式实施，旧读取路径仍可保留。

### 阶段 3：测试先行，建立不变量

目的：先把正确结构变成失败测试，再实现。

最低测试集：

- 同一项目任务在全局和项目视图出现，但数据库只有一条记录。
- 项目改名后，历史决策、任务、事件仍由同一 `project_id` 关联。
- 项目合并后，无重复记录、无悬空引用、审计链完整。
- 未确认项目不会创建正式状态、待办、决策、归档或日志集合。
- 日志新增不会改变当前状态或下一步。
- 决策被替代后，默认查询只返回当前有效决策，历史仍可追溯。
- 归档只保存关闭摘要/快照，不复制完整事件流。
- 并发修改发生版本冲突时不会静默覆盖。
- 事务失败不会出现“任务已完成但状态未更新”的半成功结果。
- 不同项目/用户之间无法越权读取。
- “当前工作是什么”的标准读取路径不需要扫描项目日志。

门禁 G3：

- 新增测试在旧实现上能够揭示缺口。
- 测试全部使用临时环境、fixture 或本地隔离数据库；无真实生产写入。
- 验收输出包含命令退出码、通过/失败/跳过数量和脱敏诊断摘要。

### 阶段 4：实现统一记录与派生视图

目的：实现单一写入路径和两级读取视图。

实施顺序：

1. 稳定 `project_id`、作用域约束及版本字段。
2. Canonical service 层：状态、任务、决策、归档快照、事件。
3. 原子写入与审计事件。
4. 全局聚合查询和项目过滤查询。
5. API 与 MCP 共用同一 service，禁止各自复制业务逻辑。
6. UI 将“五视图”呈现为标签页或查询入口，而不是五套独立存储。
7. 增加 `project_views_v2` 或等价功能开关，默认先关闭。

门禁 G4：

- 单元、集成、RLS、并发和回归测试通过。
- 任意视图记录可追到同一 canonical ID。
- 关闭功能开关时，现有行为不受影响。

### 阶段 5：旧数据盘点、干跑与迁移

目的：保留历史，不把旧混乱直接复制到新结构。

迁移步骤：

1. 对旧 Markdown 和数据库记录做只读快照，生成校验清单。
2. 解析旧全局/项目状态、待办、决策、归档、日志。
3. 按“记录类型、作用域、项目 ID、有效性、来源、时间、置信度”分类。
4. 识别重复项、矛盾项、已撤回结论和仅有日志证据的临时结论。
5. 先生成 dry-run 报告，不写入数据库。
6. 人工审核高风险项：跨项目决策、项目别名冲突、无项目 ID 记录、相互矛盾的当前状态。
7. 导入时生成稳定 ID 和来源映射；重复项只建立引用，不复制正文。
8. 旧 `project:clued/日志.md` 作为 legacy history 保留，不删除、不当作当前状态来源。
9. 校验数量、哈希、引用完整性和抽样语义。

门禁 G5：

- 干跑报告获批。
- 导入前后记录数量差异可解释。
- 没有丢失来源、时间、理由、失败、阻塞、撤回结论或证据。
- 旧数据仍可只读访问并可回滚。

### 阶段 6：更新路由、Skill 与可读镜像

目的：让所有入口遵守同一语义，而不是用提示词补救底层重复。

任务：

- 更新 Clued Continuity Skill、AGENTS/路由文档、API/MCP 说明和 UI 文案。
- 明确读取顺序：全局注册与优先级 → 项目状态/待办/决策 → 必要时日志/归档。
- 明确写入顺序：写 canonical 记录 → 同事务审计 → 视图自动反映。
- Markdown 输出采用两级五视图目录，但内容为查询结果或稳定 ID 引用。
- 防止 Skill 自行创建未经确认的项目或双写文件。

门禁 G6：

- 同一问题通过 UI、MCP、API、Skill 得到一致的记录 ID 和结论。
- 日志不会再架空状态、待办和决策。
- 文档与实际实现一致，无尚未实现的能力声明。

### 阶段 7：集成评审，不进入生产

任务：

- 在干净临时 clone 中复现构建与测试。
- 核对 HEAD、分支差异、冻结区零改动和无真实网络写入。
- 生成变更清单、风险清单、迁移报告和回滚演练结果。
- 经授权后才允许 push 或创建 PR；本计划阶段默认停止在本地评审结果。

门禁 G7：

- 构建、类型检查、Lint、单元/集成/RLS/并发测试全部达到约定标准。
- 所有失败与跳过项有明确解释。
- 未修改生产、未发布、未删除旧数据。

### 阶段 8：独立批准后的生产迁移与发布

该阶段不是本计划的默认执行范围，必须另行授权。

若获授权，顺序为：

1. 生产备份与恢复演练。
2. additive 数据库迁移。
3. 迁移 dry-run 与小范围 canary。
4. 双读校验，仍保持单写 canonical。
5. 开启少量用户的 `project_views_v2`。
6. 观测错误率、重复率、冲突率、召回准确性与权限审计。
7. 扩大启用范围。
8. 稳定期结束后再单独审批旧读取路径下线；不立即删除历史数据。

正式生产入口始终按 `clued.pixelgrav.com → Cloudflare Worker clued-cloud` 管理；ChatGPT Sites 不作为生产替代品。

## 6. 分支与变更策略

- 不在旧错误草稿分支上继续实现。
- 实施时从最新 `main` 建立新的集成分支，建议命名：`feat/clued-two-level-views-v1`。
- 保留 `feature/clued-project-lifecycle-v1` 已有提交历史，通过常规 merge 进入新集成分支；不 rebase、不 force push、不 amend/squash。
- Memory CRUD 与项目生命周期的冲突必须在新集成分支解决。
- 每个阶段形成独立、可审阅提交；schema、服务、迁移、路由/Skill 分开。
- 未通过前一阶段门禁，不进入后一阶段。

## 7. 回滚策略

| 风险 | 预防 | 回滚 |
|---|---|---|
| 新视图结论错误 | 功能开关、双读对比 | 关闭 `project_views_v2`，恢复旧读取路径 |
| 数据迁移分类错误 | 快照、dry-run、来源映射 | 停止导入，按批次撤销新增记录 |
| 记录重复 | 唯一约束、幂等键、canonical ID | 合并重复引用，不删除原始证据 |
| 项目改名/合并断链 | 稳定 `project_id`、别名表 | 恢复 alias/merge 映射 |
| 并发覆盖 | 乐观锁/事务 | 回滚事务，保留冲突版本人工处理 |
| 权限泄漏 | RLS、跨项目测试、最小授权 | 关闭新读取入口，审计访问记录 |
| Skill 路由错误 | schema 定稿后再改 Skill | 恢复 Skill 权威基线版本 |

数据库变更优先采用 additive migration。旧字段、旧 Markdown 和旧读取路径在新结构完成验收与稳定期之前不删除。

## 8. 验收指标

### 8.1 结构验收

- 全局和项目五视图均可使用。
- 任一跨层重复展示都指向同一记录 ID。
- 总表中不存在复制的项目正文。
- 项目改名、合并后引用稳定。

### 8.2 语义验收

- “当前状态”“下一步”“有效决策”“历史证据”“已归档内容”各自来源唯一。
- 日志只能补充证据，不能改变当前权威结论。
- 归档是关闭快照，不是第二份日志。

### 8.3 工程验收

- API、MCP、UI、Skill 使用同一 service/语义合同。
- 幂等、并发、事务、RLS、审计和迁移测试通过。
- 构建、类型检查和 Lint 通过。
- 验收报告包含命令、退出码、测试统计、HEAD 与工作区状态。

### 8.4 安全验收

- 无真实生产写入。
- 无跨用户或跨项目泄漏。
- doctor/日志/报告中的敏感信息已脱敏。
- 冻结区、DNS、生产 Worker 均无变化。

## 9. 完成定义（Definition of Done）

只有同时满足以下条件，才算结构重构完成：

1. 两级五视图的语义合同已确认并实现。
2. 底层每条信息只有一个 canonical 记录。
3. 全局视图通过聚合/索引生成，项目视图通过 `project_id` 过滤生成。
4. 日志、状态、待办、决策、归档不再互相替代。
5. 旧数据完成可验证迁移，来源和历史未丢失。
6. 项目改名、合并、忽略、恢复、并发和权限测试通过。
7. UI、API、MCP、Skill 与 Markdown 镜像行为一致。
8. 通过独立生产发布门禁；在此之前只能称为已实现/待发布，不能称为生产完成。

## 10. 批准后的唯一下一步

只启动阶段 0 和阶段 1：

1. 核验相关分支与最新 `main` 的真实差异。
2. 输出错误草稿分支的“保留/丢弃”差异清单，但不删除分支。
3. 基于现有项目生命周期和 Memory CRUD 写出《两级五视图语义合同》ADR。
4. 把上述不变量写成测试规格。
5. 提交 ADR 与测试规格给用户确认。

在用户确认 ADR 前，不改 schema、不迁移旧数据、不改 Skill、不合并、不部署。
