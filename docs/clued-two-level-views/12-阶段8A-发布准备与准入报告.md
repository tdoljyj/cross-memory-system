## 4. 阶段 8B 的五个独立批准点

为避免一句“上线”同时授权多种高风险动作，阶段 8B 拆成五个短步骤；每一步都需明确批准，前一步失败即停止：

1. `8B-1`：只读冻结生产基线，创建备份，并在隔离目标完成恢复演练。
2. `8B-2`：只应用 additive migration；功能开关保持关闭。
3. `8B-3`：部署无正式域名路由的 `clued-cloud-canary`，只由测试账号访问。
4. `8B-4`：导入一个 5–10 条的低风险批次并双读核对；26 条 manual-review 不进入自动批次。
5. `8B-5`：观测通过后才部署正式 Worker；扩大范围与旧路径下线仍另行批准。

## 6. Canary 方案

当前 `PROJECT_VIEWS_V2` 是 Worker 级全局开关，不能可靠按 user ID 放量。为保持实现简单且不误伤正式流量，首个 canary 不直接切 `clued.pixelgrav.com`：

1. 以同一候选构建部署独立 Worker `clued-cloud-canary`；
2. 不配置正式自定义域名或 DNS route，只保留受控 `workers.dev`/preview 地址；
3. 复制所需 Binding/secret 时逐项核对，`PROJECT_VIEWS_V2=true` 只存在于 canary；
4. 仅测试账号执行新增、查看、编辑、删除、归档/恢复、Task 完成 + State 推进和版本冲突；
5. 第一批只导入 5–10 条低风险 candidate，`source_ref` 必须携带唯一 batch ID；
6. canary 通过后，正式 Worker 仍先以开关关闭的候选版本部署；再次批准后才启用正式 V2。

这条路径不需要新增 DNS，不改变正式入口，成本只是一份短期 Worker 部署；canary 结束后可停用，但删除 Worker 仍需单独确认。

发生停止线时，不继续“观察看看”，直接执行回滚。

## 8. 回滚卡

按以下顺序处理，不默认 DROP schema，不删除原始证据：

1. 停止导入，关闭 canary 访问；正式环境则把 `PROJECT_VIEWS_V2` 设回关闭。
2. 恢复已记录的上一 Worker version：

   ```powershell
   npx wrangler rollback <LKG_VERSION_ID> --name clued-cloud --yes --message "Clued V2 canary rollback"
   ```

3. 复验 `/healthz`、legacy CRUD、MCP tools/list 和正式首页。
4. 保留 additive schema 与已生成审计；按 batch ID 将本批新增 canonical records 归档/失效，不物理删除历史证据。
5. 只有确认发生数据库破坏且普通回滚无效时，才提出“从已验证恢复点恢复生产”的单独批准；恢复前仍先在隔离目标复现。
