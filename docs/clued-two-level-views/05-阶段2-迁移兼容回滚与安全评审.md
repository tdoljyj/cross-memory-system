## 1. 实施批次

阶段 4 才创建迁移文件，并必须先运行 `supabase migration new <descriptive-name>` 获取合法文件名。阶段 2 不手写迁移编号。

计划批次：

1. **P2-A：项目生命周期前置**  
   按现有历史应用迁移 003；功能标志仍关闭，不接 API/UI/MCP。
2. **P2-B：Unified Record additive migration**  
   扩展 `clued_memories`、`clued_context_events`、`clued_audit_receipts`，添加约束和索引。
3. **P2-C：安全与写核心**  
   收紧旧直写策略与列权限；创建 private core、显式授权 wrapper、`security_invoker` 视图。
4. **P2-D：验证**  
   本地隔离数据库运行迁移、RLS、并发、回滚测试；功能标志仍关闭。

每个批次都必须可独立审阅；不修改已提交迁移 001–003 的历史内容，后续加固通过新 additive migration 完成。

## 2. 向前迁移顺序

### 2.1 预检

- 核对实际已应用 migration list，禁止只按仓库文件推断。
- 统计 `clued_memories` 各字段空值、标题/正文长度、重复 ID 与当前 grants/policies。
- 确认 003 尚未应用时，先在本地隔离库执行 001 → 002 → Memory CRUD → grants hardening → 003。
- 对现有记录生成只读行数和 ID/hash 清单；不把生产“当前 0 行”当永久假设。

### 2.2 扩展 `clued_memories`

1. 新字段先以兼容默认值加入：existing row → `note/global/active/version=1/priority=0`。
2. `project_id` 与自引用列先保持可空，建立外键和索引。
3. 跨字段 CHECK 先 `NOT VALID`，回填验证后再 `VALIDATE CONSTRAINT`。
4. 创建 Global/Project current State 与 active Decision partial unique indexes。
5. 不改 `id/title/content/created_at/updated_at`，旧 REST contract 原样可读。

### 2.3 扩展 Event 与 Receipt

- Event 关联列全部可空，历史事件无需伪造 record/project 关系。
- Receipt 幂等列可空，历史回执无需回填假 key。
- 唯一索引只覆盖 `idempotency_key is not null` 的新记录。
- 未来 V2 写入必须同时填 `record_id/record_version` 与 receipt request hash。

### 2.4 创建派生视图与函数

- 所有视图使用 `WITH (security_invoker = true)`。
- private core 使用 `SECURITY DEFINER SET search_path = ''`，所有对象写全限定 schema。
- public wrapper 只验证/解析调用身份后委托 core；逐签名撤销 PUBLIC 默认 EXECUTE，再只授予目标角色。
- 创建完成后显式 `NOTIFY pgrst, 'reload schema'`。

## 3. 旧读取/写入兼容

### 3.1 功能标志关闭

- 现有 `/api/memories` 继续只读写 global `note`，响应字段不变。
- 当前项目 API/MCP 继续使用迁移 003 的项目生命周期合同。
- Continuity checkpoint/log 路径不改，但被明确标为 legacy；不用于 V2 current 查询。
- V2 视图、wrapper 和新增列没有调用方，因此旧 Worker 可继续运行。

### 3.2 防止旧直写破坏 V2

现有 `authenticated` 对 `clued_memories` 有整表 CRUD 权限。Stage 4 迁移需改成：

- SELECT：本人全部记录，便于未来视图工作。
- INSERT 列权限：只允许 `user_id,title,content`；未给出的 V2 字段使用安全默认值。
- UPDATE 列权限：只允许 `title,content,updated_at`。
- DELETE：仅 legacy `note/global`。
- INSERT/UPDATE/DELETE RLS：除本人所有权外，再限制为 `record_type='note' and scope='global' and project_id is null`。

因此旧 Worker 无需修改即可继续 CRUD note，但无法伪造 State/Task/Decision/Archive 或改写 V2 关系、版本和状态。V2 记录只能通过事务 wrapper 写入。

## 4. 唯一事务写核心

未来核心建议签名：

`clued_private.record_write_core(p_user_id uuid, p_binding_id uuid, p_input jsonb) returns jsonb`

事务顺序固定为：

1. 解析 action、record type、expected version、idempotency key；计算 canonical request SHA-256。
2. 校验用户、scope、项目归属、confirmed/dismissed/merged 状态。
3. 按 `project_id`、再按 `record_id` 升序获取 advisory/row locks，避免反向锁死。
4. 插入带唯一 idempotency key 的 pending receipt；并发同 key 在唯一索引处串行化。
5. 已有 key：摘要相同返回原结果，摘要不同返回 `idempotency_key_conflict`。
6. 校验 expected version；不匹配返回 `record_version_conflict`，不更新任何业务记录。
7. 执行一个业务意图所需的记录变更；多记录动作仍在同一函数内完成。
8. 追加一条结构化 Event，并更新 receipt 的对象 ID、版本和脱敏结果 metadata。
9. 返回 `record_id/version/event_id/receipt_id`；任何异常回滚全部步骤。

函数内不得执行 HTTP、Worker 调用或长时间计算；锁只覆盖数据库变更。`clued_memory_audit` trigger 可继续产生 digest-only 技术审计，但不参与业务返回。

### 原子复合动作

- `complete_task_and_advance_state`：锁 Task、State 与候选 next Task；Task 完成、State 引用前移、Event、Receipt 四者同成败。
- `supersede_decision`：锁旧 Decision；创建新 Decision、旧条 superseded、双向可追溯关系、Event、Receipt 同成败。
- `archive_and_restore`：归档记录不可变；恢复时新建 current 记录并设置 `restored_from_id`。
- `merge_project`：锁源/目标项目及冲突 State；不复制正文，归档源 current State，新写入目标。

## 5. RLS 与授权设计

| 对象 | authenticated | anon | private/core |
|---|---|---|---|
| `clued_memories` | 本人 SELECT；受限 legacy note CRUD | 无 | core 可执行 V2 事务 |
| `clued_projects/mentions` | 本人 SELECT | 无表权限 | 既有 token wrapper/core 写入 |
| `clued_context_events` | 本人 SELECT | 无表权限 | 仅 core append |
| `clued_audit_receipts` | 本人 SELECT | 无表权限 | 仅 core 写入 |
| V2 views | 本人 SELECT，底表 RLS 生效 | 无 | 不写 |
| public account wrappers | 显式 EXECUTE | 无 | 委托 private core |
| public binding wrappers | 无 | 仅指定函数 EXECUTE | 先解析 token hash/scopes |

硬要求：

- 所有 public 表启用 RLS，并为 `user_id` 建首列索引。
- 策略使用 `TO authenticated` 与 `(select auth.uid())`。
- UPDATE 同时有 `USING` 与 `WITH CHECK`。
- RLS 与 GRANT 分别审计；没有“开 RLS 就等于有表权限”的假设。
- 浏览器只携带用户 JWT/publishable key，不含 service role。
- `SECURITY DEFINER` 仅用于必须原子跨表写入的 core/wrapper，固定空 `search_path`、全限定对象、逐签名撤权。

## 6. 向后兼容验证

迁移完成但标志关闭时，必须证明：

1. 旧 Memory create/list/update/delete 和 digest audit 合同仍通过。
2. 旧项目 observe/list/update/merge 合同仍通过。
3. 旧 Worker 不读取新增列也不依赖 V2 view/function。
4. Existing note ID、标题、正文、时间戳不变。
5. 迁移不会创建任何 Global/Project 正文副本。
6. 生产未启用 003 时，Worker 仍保持当前 Memory CRUD 行为。

## 7. 回滚矩阵

| 变更 | 首选回滚 | 结构回滚条件 |
|---|---|---|
| 迁移 003 项目表 | 功能标志关闭、对象闲置 | 仅在无项目写入且独立审批后 DROP |
| Unified Record 新列/索引 | 旧 Worker 忽略新列 | 仅在无 V2 写入、无依赖对象时删除 |
| V2 views/wrappers | REVOKE EXECUTE/SELECT 或 DROP view/function | 随时可重建，无业务正文 |
| RLS/列权限收紧 | 恢复上一份精确 grants/policies | 不允许 `GRANT ALL` 粗放恢复 |
| Event/Receipt 关联列 | 停止 V2 写入，历史列保留 | 仅无 V2 数据时删除 |
| 项目 merge | 关闭 V2；按审计映射人工恢复 registry | 不通过 DROP schema 伪造回滚 |

一旦存在 V2 正式记录，数据库默认回滚策略是“**关功能标志 + 恢复旧 Worker + 保留 additive schema/data**”，不是 DROP。结构性删除必须另行批准并有数据导出。
