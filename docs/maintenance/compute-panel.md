## 怎么运行

`.github/workflows/clued-compute-panel.yml`，每 5 分钟一次，只用工作流自带的 `GITHUB_TOKEN`，没有任何 Secret 进入资源池：

1. `admission-gate`：与其他自建工作流相同的门禁；定时事件直接准入。
2. 6 个 `compute-probe / <runner>` 作业，各走一条字面路由，核对机器名并打印一行 `COMPUTE_PANEL_PROBE {...}`（磁盘空闲、可用内存）。
3. `compute-panel` 作业：先跑 `tests/test_compute_panel.py` 自检，再运行 `scripts/ci/self-hosted/compute_panel.py` 重建 Issue。

新一轮运行会取消上一轮，所以离线机器最多只挂着一个排队中的探测。

除了每 5 分钟的定时运行，也可以在 Actions 里手动运行（workflow_dispatch）。GitHub 对 `*/5` 的定时常有推迟或跳过：#935 合入后的第一个小时里一次也没跑。

## 判定规则

| 状态 | 条件 |
|---|---|
| 在线、忙 | 这台机器正在跑别的工作流的作业 |
| 在线、闲 | 最近 12 分钟内有一次探测成功，或正在跑本面板自己的作业 |
| 离线 | 不忙、12 分钟内没有成功探测，且连续两轮的探测在本轮门禁通过 4 分钟后仍没有机器接 |
| 未知 | 探测不足以判断（例如定时触发被 GitHub 推迟、门禁失败或被跳过） |

“忙”只看最新 20 个运行中的工作流；被更早的长作业占着的机器可能显示为未知或离线（告警文字写“离线”，实际也可能是长时间忙）。

告警：通用池机器离线、磁盘空闲低于 20 GB、可用内存低于 1 GB、常驻执行器状态为 error（停机，或状态长时间未更新）。停机状态在该节点出现更新的“排队/运行中/已完成”状态后清除；停机期间仍会写的“落后 main”等提示不算。告警评论先发，再保存告警状态；评论失败只记在面板末尾，面板照常更新，下一轮重发。

CI 停摆（看板第 26 行缺口②）：开着的非草稿 PR 当前 head 上，最新的常驻状态是 pending 或 error（在等常驻执行器），而 30 分钟内没有任何节点在这个 head 上写过“当班”；最新状态是 error（HALT，或执行器状态长时间未更新）则立即算。30 分钟即常驻的 `DUTY_WINDOW_MS`：当班节点每 14 分钟（`DUTY_REFRESH_MS`）在每个排队提交上重写一次“当班”，超过 30 分钟没有就是无人当班（PAUSED、暂停接新、熔断、节点断电或 companion 停了都在内）。数据只来自 PR 上的 `resident-queue/<节点>` 状态，不读节点本地文件；只有最新状态既不是“当班”也不是 error 的 head 才多读一次它的状态历史，找最后一次“当班”的时间。整个停摆是一条告警（键 `stall`），期间 PR 增减、文字变化不再重发，全部恢复时说一次“已恢复”。

批次：一个 PR 提交上出现过“运行中”的常驻状态才算一个批次；排队时长从该提交第一条“排队”状态（没有则视为立即开始）算到第一次“运行中”；结果取最后一条状态，停机（error）记为失败；同一提交的重试合为一个批次。只出现“落后 main”等提示、从未运行的不算批次。批次指标大约每小时采集一次，只读最近 50 个更新过的 PR，PR 很多时 7 天窗口会少算。

请求量：每轮通常约 15–25 次 API 请求，CI 高峰时最多约 40 次，另加每小时一次约 51 次的批次指标（共享 `GITHUB_TOKEN` 每小时 1000 次）。剩余额度低于 300 时进入省额度模式：只看 5 个运行中的工作流、沿用上一轮常驻状态、跳过磁盘/内存日志和批次指标，每轮约 12 次。某一部分读取失败只在面板末尾注明，面板和告警照常发布。

## 重复执行

规则 `41ab823a`：同一提交的同一项检查只真跑一次。面板大约每小时读一次最近 3 天内更新过的 30 个 PR（含已合并、已关闭）的当前 head，用 `checks: read` 读出该 head 的全部检查运行（`filter=all`，不只是每个名字的最新一条）和该 head 的工作流运行，按下面的规则数“真跑”。同一检查数到两次及以上，在“重复执行”表里列出，并在 Issue 下发一条动态评论（@ Owner），每件只说一次；同一件的次数增加时再说一次。面板第一次带上这个功能运行时只记录、不发。

怎样算“真跑”：

- 算：已完成且结论为 success、failure 或 timed_out 的运行；或已经开始、还在进行并且已跑满 10 分钟的运行（刚开始的可能是马上被后一次取代而取消的副本，不算）。常驻“native”发布按作业计：同一个作业发布两次是一次真跑。
- 不算：skipped、cancelled（被取代的取消副本）、neutral、排队中未开始的；常驻自己的控制检查——以 `kooyumi-` 开头的检查（`kooyumi-work-admission` 每次尝试都会重发一次准入，`kooyumi-admission-verified`、`kooyumi-merge-slot` 在第 8 段每次复查都重发）和 kind 为 `native-work-admission`、`control` 的；转发托管结果的常驻检查（kind 含 relay）；各工作流里的 `admission-gate`（等 Clued 准入，不是 CI 工作）。
- 常驻的检查靠 `external_id` 的 `independent-ci:<kind>:` 前缀认出（扫描类是 `staged`，第 N 次尝试写在 `:aN`）。

怎样对上同一项检查：常驻的 `gitleaks`、`trivy`、`contract-placement` 与托管（自建池上的工作流）作业 `gitleaks-hosted-executor`、`trivy-hosted-executor`、`contract-placement-hosted-executor` 是同一项检查（去掉 `-hosted-executor` 或 ` (hosted)` 后缀）。其余托管作业按“工作流文件::作业名”区分，所以不同工作流里同名的作业是不同的检查。

原因标注：`cross-executor`（托管与常驻各跑一次）、`after-merge`（有一次运行开始于该 PR 合并之后，即已合并的 PR 又被调度）、`same-executor`（同一执行方重复：重跑、第二次尝试或第二个触发事件）。

请求量：每个要读的 head 2 次请求（检查运行 1 页，工作流运行 1 页；检查多于 100 条时多读页，最多 5 页，翻页时重复出现的同一个检查运行只算一次）。已关闭（含未合并）、最近一次更新没变、且关闭或合并已超过 24 小时的 PR 不再重读，沿用上次结果；因此稳态下大多是开着的 PR 和最近关闭的 PR，每小时约 20–40 次，剩余额度低于 300 时不读。两个 PR 共用一个 head 时，同一 head 的同一项检查只算一项（取次数多的）。读取失败（例如没有 `checks: read`）只在面板末尾注明，沿用上一次结果。

可靠性与保存：

- 每个读取请求（PR 列表、检查运行、工作流运行）遇到 5xx、网络错误、被截断的回复或读不出的 JSON，最多试 3 次，间隔 2 秒、4 秒；其他错误（例如 403 没有权限）不重试。重试后整次扫描仍失败，记下 `duplicates_failed_at`，15 分钟内不再开始新的扫描（面板末尾注明“上次读取失败”），之后才再试，不会每 5 分钟从头再来。某个提交 GitHub 不返回（404、410、422）时只跳过它并在面板上注明个数，沿用它以前的结果，不让整次扫描作废；扫描中途额度不足不算读取失败，不进入 15 分钟等待。全部提交都读不到时算扫描失败（走上面的 15 分钟等待），不记为“没有发现”。第一次扫描（或之后）读不到的提交，等它们能读时，里面已有的重复只记录、不公告，之后的新重复照常公告。
- 保存的结果里，最近 12 项带完整明细，再往后最多 80 项只存短记录（PR、提交、检查、次数、最近一次），所以“共 N 项”和已关闭 PR 的沿用都按总数算，不会随明细截断而变少。超出这 92 项的提交不记为“已定稿”，下一次扫描会重读，总数仍然准确（代价是多几次请求）。检查名和标签各截到 80 字符（超长的名字保留一个摘要，仍能区分），标题截到 60 字符。
- 已说过的重复执行键单独存放（最多 300 个，每个存 12 位摘要），和合并、批次失败等其他动态的 200 件上限互不挤占；保存下来的那 92 项发现，其键不会被淘汰，所以不会重复提醒（超出 92 项的提醒键按先后淘汰，需要一个窗口内出现 300 个以上发现才会发生）。Issue 正文有 65536 字符的上限：写入前如果正文超过 60000 字符，依次丢掉短记录、运行明细（表格的“构成”列改按各执行方的次数显示）、只留表格的 10 行；仍超过就只留总数，面板上写明“明细已省略”；最后一档连机器可读数据里的事件也省去（事件已在评论里）。被丢掉的提交下次扫描重读，总数仍然准确，已说过的键和“读不到的提交”记录都保留，所以不会重复提醒。最坏情况（92 项加满、检查名 250 字符、标题 300 字符、400 件其他动态）实测约 77500 字符，经上面的收缩降到约 51000，测试里有断言。 每次扫描读的 PR 不超过 30 个，所以读不到的提交记录最多 30 项，不设别的上限。

## 已知限制

- 注册列表需要管理员令牌，`GITHUB_TOKEN` 读不到，所以通用池名单写在脚本里；新增机器要改 `POOL`。
- 面板本身跑在通用池上：整池掉线时面板也停更，由托管的 `clued-ci-health` 从池外发现（托管免费分钟每月重置，Decision `183ee67c`）。Issue 上的更新时间停住即说明面板没在跑。CI 停摆告警因此也依赖通用池；没有放进 `clued-ci-health`，因为它的触发器、权限和作业被 `scripts/ci/validate_runner_budget_policy.py` 按哈希冻结（没有 `statuses: read`，每 6 小时一次），改它要 Owner 决定。
- 重复执行只看每个 PR 当前的 head；同一 PR 以前被强推替换掉的 head 不读。常驻第 2 次尝试里重跑的扫描、托管与常驻并行跑的扫描都算真跑；常驻自动尝试 2 是 Owner 决定 `1b5d3687` 允许的重跑，面板照实列出，由人判断。
- 4 台 Linux 全部被占满超过 5 分钟时，新一轮会取消还在排队的面板作业，面板暂时停更，期间的常驻停机也不会告警。
- GitHub 的定时触发可能推迟；离线判定需要连续两轮，通常在 10–15 分钟，推迟时更晚。
- Task `679a0c2b` 里尚未完成的部分：不稳定测试识别与隔离、在 KooYomi 里查询面板、抽查批次数字与执行器账本一致、告警送达的实测。
