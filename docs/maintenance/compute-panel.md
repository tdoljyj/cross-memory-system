## 看哪里

仓库里标题为“算力面板（自动更新）”的 Issue，由 `github-actions[bot]` 维护，正文每 5 分钟原地更新：

- 通用池 6 台（company-linux-01..04、company-win-01、home-win-01）：在线/离线/未知、忙/闲、当前作业、能接的活、磁盘空闲、可用内存、24 小时利用率、最近一次探测。
- 其他机器：各常驻执行器（从 PR 上的 `resident-queue/<节点> (info only)` 状态自动发现）、DESK-W-591（待安装）、home-linux-01（已退役）、home-win-02（控制机，不计入算力池）。
- 常驻批次指标（1 天与 7 天）：批次数、通过、失败、失败率、排队时长中位数与 P90、批次时长中位数、重试次数、烧头次数。Task `7f205c71` 的触发指标取这里（Decision `d8e3dea4`）。
- 正文末尾的“机器可读数据”是 `clued.compute-panel/v1` JSON，供脚本读取。

告警开始或结束时，在同一个 Issue 下发一条评论，新告警会 @ 仓库 Owner。

## 怎么运行

`.github/workflows/clued-compute-panel.yml`，每 5 分钟一次，只用工作流自带的 `GITHUB_TOKEN`，没有任何 Secret 进入资源池：

1. `admission-gate`：与其他自建工作流相同的门禁；定时事件直接准入。
2. 6 个 `compute-probe / <runner>` 作业，各走一条字面路由，核对机器名并打印一行 `COMPUTE_PANEL_PROBE {...}`（磁盘空闲、可用内存）。
3. `compute-panel` 作业：先跑 `tests/test_compute_panel.py` 自检，再运行 `scripts/ci/self-hosted/compute_panel.py` 重建 Issue。

新一轮运行会取消上一轮，所以离线机器最多只挂着一个排队中的探测。

## 判定规则

| 状态 | 条件 |
|---|---|
| 在线、忙 | 这台机器正在跑别的工作流的作业 |
| 在线、闲 | 最近 8 分钟内有一次探测成功，或正在跑本面板自己的作业 |
| 离线 | 不忙、8 分钟内没有成功探测，且有一次探测创建 4 分钟后仍没有机器接 |
| 未知 | 探测不足以判断（例如定时触发被 GitHub 推迟） |

告警：通用池机器离线、磁盘空闲低于 20 GB、可用内存低于 1 GB、常驻执行器状态为 error（停机，或状态长时间未更新）。

批次：一个 PR 提交上出现过“运行中”的常驻状态才算一个批次；排队时长从该提交第一条常驻状态算到第一次“运行中”；结果取最后一条状态。只出现“落后 main”等提示、从未运行的不算批次。批次指标大约每小时采集一次（最近 30 个更新过的 PR），其余每轮采集。

## 已知限制

- 注册列表需要管理员令牌，`GITHUB_TOKEN` 读不到，所以通用池名单写在脚本里；新增机器要改 `POOL`。
- 面板本身跑在通用池上：整池掉线时面板也停更，由托管的 `clued-ci-health` 从池外发现（托管免费分钟每月重置，Decision `183ee67c`）。Issue 上的更新时间停住即说明面板没在跑。
- 4 台 Linux 全部长时间被占满时，门禁和面板作业排不上，面板会暂时停更。
- GitHub 的定时触发可能推迟，离线判定通常在 10 分钟左右，推迟时更晚。
- Task `679a0c2b` 里尚未完成的部分：不稳定测试识别与隔离、在 KooYomi 里查询面板、抽查批次数字与执行器账本一致、告警送达的实测。
