## 0. 核心裁决

原 R5 计划方向正确，但执行合同过重：K4～K10 全部串行，语义召回、100 次 Shadow、双实体设备、完整灾备、迁移和独立终审共同阻塞产品收口，投入产出不合理。

R5.1 不降低核心质量，只改变验收方式：

1. 安全、租户隔离、幂等、冲突、删除、撤销和日志隐私继续零容忍；
2. K3 已完成，不重新设计、不重复实施；
3. K3 的 PostgreSQL 集成测试只在最终候选环境补跑一次，不为重复取证单独开 Gate；
4. 旧 K4～K10 收敛为 4 个必做 Gate；
5. 每个 Gate 跑专项测试，完整回归只在最终 Gate 跑一次；
6. 一个执行 Agent 可以连续完成 K4～K6，只有发生硬阻断才停下等待；
7. MIV-005A / Cloud FTS 可以支撑首个 Beta，语义召回不再阻塞基础产品发布；
8. 语义召回只有在准备启用该功能时才进入独立 S1 Gate；
9. 不再采用旧 R4 的 one-shot、100 次 Shadow和多角色隔离仪式；
10. 所有测试使用合成数据或明确脱敏数据，不接触 production 用户数据。

目标终态调整为：

~~~text
CLUED KERNEL BETA CANDIDATE
safe lexical recall enabled
semantic recall disabled or separately qualified
production deployment still requires explicit authorization
~~~

## 2. 适中门槛的定义

“门槛别太高”不等于低门槛。R5.1 将验收分成三类。

### 2.1 绝不降低的硬门槛

以下任意一项出现 1 次即对应 Gate FAIL：

- 跨租户正文泄漏；
- Secret 被保存、召回或写入普通日志；
- Scope、Deleted、Quarantined、Superseded 或 Conflict loser 被绕过；
- 同一幂等请求生成重复版本；
- Tombstone 被旧设备或旧 Outbox 复活；
- 被撤销的 Device 或 Binding 仍能写入或读取；
- 降级路径扩大权限；
- migration 或升级破坏现有 Canonical 数据且无法恢复；
- 未经授权修改真实 Binding；
- 测试写入 production 数据。

### 2.2 允许采用工程目标的门槛

以下项目不追求生产级极限指标，只要求 Beta 可用：

| 项目 | R5.1 门槛 |
|---|---|
| 普通云端写入 | staging 合成数据 p95 ≤ 3 秒 |
| 安全词法召回 | staging warm p95 ≤ 2 秒 |
| 本地 fallback | p95 ≤ 500 ms |
| 1,000 个 Change Event 同步 | ≤ 2 分钟 |
| Outbox 恢复 | 无丢失、无重复版本；速度记录但不设苛刻吞吐门 |
| 测试稳定性 | 同一冻结环境连续运行 2 次无随机失败 |
| 资源成本 | dev/staging 月度可变成本目标 ≤ US$20，达到 US$10 发出提醒 |

这些是工程验收目标，不是对外 SLA。若测试机器明显受限，可记录硬件与网络后按相对基线判断，但不得豁免安全和一致性。

### 2.3 被删除的过度门槛

R5.1 明确删除：

- 每个 Gate 都完整重跑全部历史测试；
- 每个 Gate 都进行独立 Agent 裁决；
- 每个 Gate 至少一个人为拆分提交；
- 两台实体 Windows 电脑才算同步通过；
- 100 次 Shadow 才能继续；
- one-shot holdout 与不可重试 marker；
- 为每项功能生成单独长报告、manifest 和 transcript；
- Beta 前完成 production 级 RPO/RTO、全量 SBOM、完整 Break-glass 运维体系；
- Beta 前部署所有 Cloudflare / R2 / Container 组件；
- Beta 前必须启用语义召回。

以下六项不是背景资料、建议项或“有时间再做”，而是 R5.1 必做范围。执行 Agent 必须逐项实现或证明现有实现已经满足合同，并在对应 receipt 中填写 `borrowed_enhancements`。不得用“已有类似代码”代替测试证据。

| 编号 | 强制增强 | 执行 Gate | 最小交付 | 验收性质 |
|---|---|---|---|---|
| BE-01 | 事务式安装、升级与回滚 | K6 | 统一 lifecycle transaction state machine | 必须通过 |
| BE-02 | Adapter 真实探测与只读 Doctor | K4/K6 | probe contract + credential-boundary tests | 必须通过 |
| BE-03 | 增量索引 generation 与确定性缓存 | K5 | generation manifest + cold/incremental equivalence tests | 必须通过 |
| BE-04 | 分级证据契约 | K5 | PREVIEW/VERIFIED/AUDIT contract | 必须通过 |
| BE-05 | 严格遥测契约 | K6 | event/key allowlist + privacy gates | 必须通过 |
| BE-06 | 用 Orca 不变量补 K3 幂等测试 | K4 前置兼容增强 | K3 idempotency regression extension | 必须通过 |

#### BE-01：事务式安装、升级与回滚

统一状态至少包含：

~~~text
STAGED
COMMITTED
ROLLED_BACK
FINALIZED
RECOVERY_NEEDED
~~~

必须验证：stage 不污染当前安装；commit 前后目标文件身份复核；失败保留旧版本；重复执行幂等；进程崩溃后可恢复；symlink/reparse point、owner/ACL 和异常 link count 被拒绝；用户非 Clued 配置不被覆盖。

#### BE-02：Adapter 真实探测与只读 Doctor

必须建立统一 ProbeResult：

~~~text
AVAILABLE
MISSING
BROKEN
TIMEOUT
STALE_CREDENTIAL
DENIED
DEGRADED
~~~

探测必须实际执行一个无副作用操作，不能只检查命令、文件或配置是否存在。Doctor 运行前后对配置、token、Cookie、凭据存储和 Binding 状态做快照，要求字节和状态不变；单 Adapter 失败只影响该通道；输出必须经过 credential redaction。

#### BE-03：增量索引 generation 与确定性缓存

每个派生索引 generation 至少绑定：

~~~text
canonical_committed_seq
source_manifest_hash
provider_or_extractor_identity
schema_version
build_parameters_hash
created_at
~~~

缓存键不得只有 mtime/size。必须包含内容 hash 和 provider/extractor identity；源文件或对象在构建期间变化时不得生成混合 generation；中断 generation 不得成为 current；同一冻结输入的 cold build 与 incremental build 必须产生相同有效对象集合、排除原因、结果 ID 和稳定排序。

#### BE-04：分级证据契约

三个等级必须具有机器可判定的能力边界：

| 等级 | 允许 | 禁止 |
|---|---|---|
| PREVIEW | 快速返回候选和 provisional 标记 | 宣称不存在、完整、最终正确 |
| VERIFIED | 回源核对当前 version/generation 后回答 | 对未检查范围作全局否定 |
| AUDIT | 检查目标 Scope、分页、当前 generation，并列出未覆盖缺口 | 隐藏 incomplete/gap 状态 |

默认 Agent Recall 使用 VERIFIED。所有“没有找到”“全部”“唯一”等完备性结论必须来自 AUDIT，或显式返回 `evidence_incomplete=true`。

#### BE-05：严格遥测契约

遥测只允许预注册的 event 和 key：

- 未注册 event/key 直接丢弃；
- 字符串只能使用固定枚举或不可逆分组值；
- 数值优先分桶；
- 禁止正文、query、路径、URL credential、原始异常、token、memory ID 和 Binding ID；
- `DO_NOT_TRACK`、CI、用户关闭或无 telemetry key 时不得发送；
- gate 必须在每次发送时重新判断；
- 遥测失败不得影响产品主路径。

至少加入 allowlist 正向测试、未知字段丢弃测试、敏感字段拒绝测试、DNT/CI/disabled 测试和发送失败降级测试。

#### BE-06：用 Orca 不变量补 K3 幂等测试

这是一项 K3 兼容性测试增强，不授权重写 K3 数据模型或生命周期语义。开始 K4 前先追加以下测试：

1. 同 caller、method、request ID、payload 重放，返回同一语义结果且不新增 version/event；
2. 同 request ID 但 payload hash 不同，返回 `IDEMPOTENCY_CONFLICT`；
3. 同 request ID 但 method 不同，拒绝复用；
4. 不同 Binding 或 Device 复用 request ID，不得错误命中其他调用者 receipt；
5. transaction 已提交但响应丢失，重试返回已完成结果；
6. receipt 处于 PENDING 时并发重放，不得产生双提交；
7. stale `base_version_id` 在创建新版本前被拒绝或进入显式 conflict；
8. delete/update、resolve-conflict 重放和 Tombstone 竞态不产生重复权威事件；
9. request ID 有效期和清理策略不得破坏仍可能重放的离线 Outbox；
10. receipt 和错误日志不得保存正文或原始 payload。

BE-06 PASS 条件：新增专项测试全部通过，K3 原 12 项静态合同和 PostgreSQL 集成测试在 K7 最终环境无回归。若发现缺陷，只允许做维持既有合同的最小修复；需要改变 K3 冻结语义时必须停止请求授权。

## 4. Gate K4：Sync + Device/Binding Security

### 4.1 目标

完成在线、离线、弱网同步，并把 Account、Device、Binding 和 Scope 变成所有访问路径的强制门禁。

K4 的第一项工作必须先完成 `BE-06`：为 K3 追加 Orca 风格幂等不变量测试。BE-06 未通过，不得继续实现同步重放。

### 4.2 必做实现

1. cursor pull、ack、cursor expired 后全量恢复；
2. 有序 Local Outbox；
3. 上传成功但响应丢失后的幂等恢复；
4. base_version 过期时产生显式 conflict，不做静默 LWW；
5. Tombstone 优先于旧设备写入；
6. Device 与 Binding 可独立撤销；
7. Local IPC 身份校验和最小权限；
8. 本地副本和 Outbox 使用现有设备保护机制；
9. UI/CLI 能显示数据来源、cursor、Outbox 数、最后同步时间和降级原因；
10. Adapter 后端使用有序候选列表，并记录实际激活的 backend。

### 4.3 从第三方源码借鉴

从 Agent-Reach 借鉴：

- “命令存在”不等于可用，必须执行无副作用真实探测；
- 单个 Adapter 探测异常只让该通道 DEGRADED，不拖垮整个 Doctor；
- Doctor 只读，不刷新凭据、不创建 Cookie、不修改配置；
- 输出边界统一清洗 URL credential、token 和敏感字段；
- 私有配置拒绝 symlink，采用原子替换和 owner-only 权限；
- 所有公网抓取入口使用 SSRF-safe URL 校验。

参考：

- https://github.com/Panniantong/Agent-Reach/blob/main/agent_reach/probe.py
- https://github.com/Panniantong/Agent-Reach/blob/main/agent_reach/doctor.py

从 Orca 借鉴：

- mutation receipt 绑定 caller、request ID、method 和 payload hash；
- 同 request ID 改变 payload 必须返回 `IDEMPOTENCY_CONFLICT`；
- stale-base 请求在消耗失败预算前拒绝；
- 不因 worker 变慢就自动判定数据操作失败。

参考：

- https://github.com/stablyai/orca/blob/main/src/main/runtime/orchestration/mutation-receipt-store.ts

要求：借鉴不变量和测试方法；不引入 Orca 的多 Agent DAG 或任务编排。

### 4.4 最小专项测试

必须覆盖以下 12 个场景：

1. 正常增量 pull；
2. 离线 create 后恢复；
3. 离线 update 后恢复；
4. 上传已提交但 response 丢失；

## 5. Gate K5：Safe Recall + Essential Lifecycle Ops

### 5.1 目标

在语义召回保持关闭时，让 Clued 具备安全、可解释且足以实际使用的召回、导出、删除和恢复能力。

### 5.2 必做实现

1. Cloud FTS Provider；
2. 保留 MIV-005A Provider；
3. tenant、Binding、Scope、Secret、Deleted、Quarantined、Superseded、Conflict、Truth 和 Validity Window 硬过滤；
4. 最小披露和结果数量上限；
5. Recall Trace 记录候选、排除原因、最终选择和 provider version，但不记录正文或 query 全文；
6. 单条查看、编辑、删除；
7. JSONL 导出和 checksum manifest；
8. 账号删除的 deletion ledger 最小闭环；
9. 小规模合成数据库备份恢复一次；
10. 恢复后重放 deletion ledger 并重建索引。

Markdown 导出、复杂可视化后台、production RPO/RTO、多区域恢复和完整 Break-glass 延后，不阻塞 Beta。

### 5.3 从第三方源码借鉴

从 Codebase Memory MCP 借鉴“证据层级”，在 Clued 内采用：

~~~text
PREVIEW   快速候选，不允许宣称完整或不存在
VERIFIED  回到来源并确认当前版本
AUDIT     检查完整范围、分页、generation 和明确缺口
~~~

普通 Agent Recall 默认使用 VERIFIED；Doctor 和用户审计命令可使用 AUDIT。任何未覆盖完整范围的结果不得宣称“没有这条记忆”。

- https://github.com/DeusData/codebase-memory-mcp/blob/main/src/cli/agent_profiles.c

- 缓存键同时包含内容 hash 和 extractor/provider identity；
- 增量索引结果必须与冷构建结果一致；
- 索引刷新失败时保留旧索引并明确 DEGRADED，不破坏 Canonical 数据。

### 5.4 Recall 验收

| 指标 | 门槛 |
|---|---:|
| MIV-005A 既有回归 | 100% PASS |
| Hard-rule leakage | 0 |
| Secret leakage | 0 |
| Cross-tenant leakage | 0 |
| NO MEMORY 合同 | 100% |
| 30 个 sanity query 的预期对象进入 Top 5 | ≥ 27/30 |
| Trace 的排除原因与实际过滤 | 100% 一致 |
| 冷构建与增量索引结果 | 完全一致 |

27/30 是适中而非低门槛：允许少量自然语言表达差异，但不允许安全规则和既有能力回归。

### 5.5 Lifecycle 验收

- JSONL 导出后可在空库恢复解析；
- 单条删除立即从普通召回消失；
- 离线设备恢复后不会复活删除对象；
- 账号删除任务可重试且不会漏记 ledger；
- 备份恢复后先重放 deletion ledger，再开放普通读取；
- 普通日志和错误响应正文泄漏为 0。

## 7. Gate K7：Final Practical Review

### 7.1 目标

用一次完整、可复验但不过度仪式化的终审，判断是否形成 Clued Kernel Beta Candidate。

### 7.2 必做检查

1. 精确记录 HEAD、父提交、分支和 worktree；
2. 在同一候选 HEAD 上运行完整测试矩阵一次；

11. 输出一个最终报告，不重复生成十几份叙述性文档。

### 7.3 完整回归规则

## 14. 最终判断标准

这份计划的原则是：

> 不能为了快而牺牲安全和数据正确性，也不能为了形式完整而让产品永远无法完成。

Clued 首个 Beta 真正需要证明的是：

- 记忆写得进去且不会重复；
- 多设备/多 Agent 能同步且不会静默覆盖；
- 权限、Secret 和 Scope 不会泄漏；
- 删除后不会复活；
- 召回至少在安全词法基线上可靠可用；
- 安装、诊断、更新和回滚能真实工作；
- 整体成本与个人产品阶段相匹配。

语义模型、100 次 Shadow、多区域灾备、复杂协作编排和生产级运维，只有在核心产品已经产生实际使用价值后才值得继续投入。
