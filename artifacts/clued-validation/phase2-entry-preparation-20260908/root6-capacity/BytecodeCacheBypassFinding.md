# 发现：控制器目录里的 `__pycache__` 是一条已证实的源码完整性绕过

**状态：`FINDING_NO_WRITE_PERFORMED`。** 未写库、未注册代际、未消耗预算。

由实施方在第十六轮之后的自查中发现 —— **不是评估者提出的**。已修复并双向拦截。

## 一句话

`.py` 的字节可以一字不动，被执行的却是 `__pycache__` 里伪造的 `.pyc`。清单、可信入口的逐文件校验、以及 `check-digest-pins.mjs` 三道检查**全部通过**。

## 为什么 `-B` 挡不住

可信入口用 `-I -S -B` 启动 python。**`-B` 只阻止「写」字节码，不阻止「读」。** 只要 `__pycache__/<模块>.cpython-311.pyc` 存在，CPython 就优先加载它，不去解析 `.py`。

时间戳式 `.pyc` 的有效性判据，是它自己头部记录的「源文件 mtime + size」。**这两个字段在 `.pyc` 里，攻击者可以直接写。**

## 实证（在临时副本上做的，未触碰真实控制器）

```
victim.py:   SECRET_LIMIT = 600

基线执行                                    600
攻击者编译 SECRET_LIMIT = 999999 的源码，
把 .pyc 头部的 mtime/size 改写成 victim.py 的值

victim.py 的 sha256                        未变（YES）
再次执行                                    999999
```

**源文件逐字节未变，行为已被替换。** 常量取 600 是有意的 —— 那正是本次运行那个 600 秒上限的量级。

## 它此刻真实存在

【实测】`control-context-verifier-root6-linux-successor/__pycache__/parent600.cpython-311.pyc`，20,370 字节，**不在 302 条清单里**，而 `parent600.py` 的 `__cached__` 正指向它。

来源是实施方自己：为枚举 `.pyc` 集合曾短暂去掉 `-B` 跑过一次 python。**一次为了做清单而临时放宽的操作，给清单本身开了一个洞。**

## 修法：删除并双向拒绝，而不是把它钉进清单

标准库那 44 个 `.pyc` 是**钉进清单**的（R14-F4 的修法），那对它们合适：它们随镜像固化、跨容器逐字节相同。

控制器自己的 `.pyc` 不同 —— 它们是**生成物**，`.py` 一改就变。把它们钉进清单等于再造一条要同步的链，而**这条链正是本轮反复出错的那一类**。所以选择删除并拒绝：

| 位置 | 行为 |
| --- | --- |
| 构建期 `check-digest-pins.mjs` | 目录内存在 `__pycache__` 即拒绝出清单 |
| 运行期 `tool-entry.functions.js` | 在逐文件校验**之前**退出 `CONTROLLER_BYTECODE_CACHE_PRESENT` |

【实测】两道都验过：无 `__pycache__` 时入口正常走到 `cli.mjs`（返回 `BOUNDED_STDIN_INPUT_REQUIRED`）；植入一个空 `__pycache__` 后，入口退出 `CONTROLLER_BYTECODE_CACHE_PRESENT`，闸门拒绝出清单。

控制器自身的模块都由显式路径加载，不需要字节码缓存，删除无副作用。
