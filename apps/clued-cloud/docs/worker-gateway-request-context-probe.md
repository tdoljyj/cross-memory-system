# Temporary Worker request-context acceptance probe

The C1 gateway JWT must be checked through the production Data API. Catalog role settings or an administrator's `SET ROLE` do not establish the settings of a real HTTP request. The reviewed gateway role normally has exactly 80 RPC grants; this probe is a temporary, explicitly authorized exception for one additional metadata RPC.

The opening migration is `20261009160000_worker_gateway_request_context_probe_v1.sql`; mandatory cleanup is `20261009160100_close_worker_gateway_request_context_probe_v1.sql`. Apply them in **separate** official `Clued Cloud production release` runs with `mode=migrate`, selecting only the respective file. Applying both in one run leaves no interval for the HTTP acceptance read. Both precise migration resources and their sequencing require production authorization before opening the probe.

The probe is `public.clued_worker_request_context_probe_v1()` with no arguments. It is `SECURITY INVOKER`, executable only by `clued_worker_gateway`, and requires the invoker, request role and validated JWT role to agree. It returns only these role names, the request's effective `statement_timeout`, and its deadline. It does not read business rows, accept SQL or request parameters, sleep, change the timeout, or weaken the Binding checks of any existing RPC.

Its first opening fixes a 30-minute deadline. Reapplying the opening migration does not extend it. Expiry refuses calls but does **not** remove the additional grant: cleanup remains mandatory. A private RLS-protected lifecycle row retains the opening time, deadline, qualified function identity and close tombstone. Replaying opening and closing migrations after cleanup preserves the closed state. Unknown same-name functions, alternate lifecycle shape, grants, policies, triggers or identity drift fail closed; cleanup never uses `CASCADE` to remove unrelated objects.

Execution and evidence:

1. Before opening, verify the live Binding, original Task, exact source commit and both migration files, production ledger/history, and the current gateway's 80 grants and original role boundary. Obtain the precise opening and closing authorization. Retain the imported signing key's public identity; keep the private key and gateway JWT in approved encrypted host storage.
2. Apply only the opening file through the official migration workflow. Capture its successful result and production history row before the next action. Confirm the fixed deadline and the temporary gateway grant; no other API role gets execution.
3. POST to `/rest/v1/rpc/clued_worker_request_context_probe_v1` with the existing publishable API key, the gateway JWT in `Authorization`, and an empty object body. Record the actual HTTP request ID and metadata. The three role fields must equal `clued_worker_gateway`; the effective timeout must be 3 seconds. The returned setting proves the actual request configuration; it does not claim that a deliberately slow production query was cancelled.
4. Apply only the closing file through the official workflow immediately after the read, including when the result is unexpected. Confirm the function is absent, the close tombstone is present and the gateway again has exactly its original 80 grants, with no table/schema/membership expansion. Confirm the HTTP route is no longer usable after schema reload. Record both history rows and add their exact ledger entries through a PR.
5. Stop C1 cutover if the actual role/timeout, cleanup or final boundary is unverified. Diagnose against exact evidence; do not restart services, lock business tables, send large payloads, borrow a service-role/secret API key, or leave the temporary 81st grant in place.

The independent database tests cover role isolation, malformed/missing claims, fixed expiry, replay, drift refusal and cleanup. The existing authorization CI entry also runs issuer-credential and gateway database suites. Production HTTP evidence, credential configuration, Worker publication, five-entrypoint verification and at least 24 hours of observation remain separate acceptance steps.

PostgREST can refresh in-database role settings while loading schema; Supabase recommends explicit config reload for role changes. These migrations notify both config and schema, but only the real HTTP read establishes the effective production value. See [Supabase timeouts](https://supabase.com/docs/guides/database/postgres/timeouts) and [PostgREST request transaction settings](https://docs.postgrest.org/en/stable/references/transactions.html).
