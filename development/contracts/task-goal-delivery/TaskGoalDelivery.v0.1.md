# Task goal and file delivery v0.1 (implementation proposal)

Status: Candidate; not deployed or accepted. Scope: D01/D02 only. Canonical Task, M1 CAS/currentness/permissions/Event/Receipt, Storage jobs, immutable persisted verification, and the existing Artifact registry remain the authorities. No second Task body, file store, execution permission, ordinary-user upload, external business action or device adapter is introduced.

## Canonical data

An existing or new schema-1 Task opts in through `type_fields.task_workflow`:

```json
{
  "contract": "clued.task-goal-delivery/1",
  "goal": "Deliver the agreed report",
  "scope": "The agreed subject and exclusions",
  "completion_level": "artifact",
  "input_versions": [],
  "acceptance_mode": "machine",
  "conditions": [{"id":"archived","kind":"file_integrity","text":"The agreed version is archived","deliverable_id":"report"}],
  "deliverables": [{"id":"report","label":"Report","required":true}],
  "delivery_refs": []
}
```

- `completion_level`: `artifact | business_effect | physical_effect`. Only `artifact` can complete in this implementation. A draft/report file never proves a cancellation, payment, repair or other business/physical result.
- `input_versions`: at most 16 `{label,kind,version,id?,scope?}` objects. `kind=record` binds an Owner-authorized canonical Record UUID, exact canonical scope and integer Record version; `kind=artifact` binds an authorized Artifact UUID and exact integer registry version. Their ownership, scope, currentness and versions are rechecked. `kind=declared` is an external version declaration, has no independent freshness proof, is always visibly unverified, and is forbidden in machine mode. An actual Native Owner may explicitly accept its limitation in owner mode.
- `acceptance_mode`: `machine | owner`. Machine mode verifies archival version/file integrity only. It requires at least one required file deliverable and only `file_integrity` conditions tied to an existing deliverable. Semantic/content quality requires owner mode and an actual Native Owner acceptance.
- `conditions`: 1–16 `{id,text,kind,deliverable_id?}` entries, unique IDs; `kind=file_integrity | owner_review`. Owner-review conditions require owner mode. These are completion conditions on the one Task, not another execution body.
- `deliverables`: 1–16 `{id,label,required,path?,mime_type?,sha256?}` entries with unique IDs and at least one required item. Optional path/MIME/SHA criteria are expectations, never proof. MIME must be present in trusted persisted verification to satisfy a MIME expectation.
- `delivery_refs`: at most 16, with at most one `{deliverable_id,job_id,goal_version}` per ID. Current-goal refs must name a current deliverable; refs from an older goal may retain a retired ID as historical metadata and never qualify the new goal. If Native binding would exceed 16, it removes only refs with both a retired deliverable ID and an older goal version from the current definition. It preserves every current-goal/current-deliverable binding, and existing immutable M1 Event/Receipt history remains available. The Job UUID references the existing authorized Storage job; there is no caller-success/hash/link/proof upload surface.
- ID strings are bounded to 80 characters; goal/scope to 4,000; label to 200; condition text to 1,000; paths to 1,000. Unknown keys/types, nulls, duplicate IDs and invalid references are rejected.

`goal_version` is a server-derived SHA-256 of Task UUID, canonical scope, title, content and the entire workflow definition excluding `delivery_refs`. Record CAS remains the integer `Record.version`. Goal/body/scope/input/condition/deliverable changes produce a new goal version; prior refs and acceptance remain historical and cannot qualify it until deliberately rebound/reaccepted. Metadata unrelated to the definition does not force another Owner permission prompt.

The opt-in marker is sticky. Removing/nulling it, replacing `type_fields` to omit it, changing away from Task/schema-1 or bypassing completion through generic M1/direct table writes must fail. Ordinary legacy Tasks without this marker keep their existing lifecycle behavior. Cancellation/archive and other non-completion updates preserve unchanged historical refs without requiring newly available source read access; this includes a Global Task whose file's source Project has closed or whose source read grant was revoked. New/changed refs and every actual completion still revalidate the source and permissions.

The existing authorized `record_list`, `search_context` and generic mutation supplemental Record add safe `task_workflow={goal_version,definition,delivery_refs,deliveries}` metadata for an opted-in schema-1 Task at the exact already-authorized returned ID/version/scope. Locator qualification revalidates each linked source using the **actual admitted Agent Binding**, both its Canonical source-scope read and the existing Storage `storage_read_evaluate_v1(...,'read')` and `storage_policy_evaluate_v2(...,'inspect',job)` evaluators. The latter preserve active policy/read generations, client registrations/capabilities, and Owner client/root/read-class denies. Canonical Task read alone cannot authorize file location or proof metadata. Any unknown/denied linked scope or Storage read/inspect returns only deliverable ID, unknown status and generic unavailable reason; no file identity, location or proof leaks. Null Binding yields canonical metadata only and never becomes an Agent Owner bypass; the separate direct Native Owner API retains its established Owner access rules. Authorized locators expose bounded file IDs, connection ID, path, version, hash, exact Receipt IDs, link and the persisted verification boundary; they do not read file content, list candidates, expose private acceptance or grant execution/Storage effects. Fail-closed anchor-count patches enrich after authorized list filtering, and enrich search matches **before existing byte-budget pagination**. The existing search cache contains lower-cased text only; locator status is derived freshly from current registry/source/Storage authorization on each read, including when the Task's text/version is unchanged. Agent updates use the same M1 `type_fields.task_workflow` path and revalidate linked-source read/Storage authorization when adding/changing refs or completing.

## Native API

`public.clued_task_goal_delivery_owner_v1(p_input jsonb)` is authenticated-only and validates the actual direct Native human session through existing `authorization_owner_v12`. Every action requires `expected_owner_id` matching the actual session Owner before reading or writing the Task. Delegated OAuth, Agent/Worker gateway, anonymous and service-role callers cannot use it. This prevents a stale tab/account switch from applying another account's displayed draft.

Common fields: `{action,id,expected_owner_id}`; mutation actions additionally require `{base_record_version,idempotency_key}`. Accepted actions and additional fields:

| Action | Additional fields | Result |
|---|---|---|
| `read` | none | Current Task workflow plus bounded delivery candidates; no writes |
| `set_goal` | `workflow` (complete definition, no `delivery_refs`) | Existing M1 update; retain old refs as historical/stale |
| `bind_delivery` | `goal_version,deliverable_id,job_id` | Existing M1 update binding the exact current goal |
| `unbind_delivery` | `goal_version,deliverable_id` | Existing M1 update removing that ref |
| `accept` | `goal_version,completion_digest` | Immutable Native Owner acceptance with M1 Event/Receipt; not Task completion |
| `complete` | `goal_version,completion_digest,closure_summary` | Existing M1 close after all current checks pass |

Unknown action-specific keys fail. Mutations validate CAS and currentness under the existing Owner currentness lock before applying the current definition. An adapter M1 receipt family `task_goal_delivery_owner` binds the exact Native action payload (including expected Owner, CAS, goal version and completion digest), before definition/CAS checks. An identical lost-reply retry replays that immutable result even after the Task becomes terminal; a different payload under the same key receives a conflict receipt. Set/bind/unbind/complete call the existing canonical M1 `record_mutation` in the same transaction using a distinct derived idempotency key. The adapter Event/Receipt links its exact underlying Record mutation Receipt; it does not write a second Task. Adapter validation failures preserve rejected/failed Receipts. Acceptance uses its adapter receipt and an immutable audit row holding only Task ID, goal version, completion digest, accepted Record version and receipt; it contains no executable body. Acceptance is not representable through `user_confirmed`, a caller `owner_accepted` flag or canonical type fields.

Response adds `{task_id,record_version,task_workflow,delivery_candidates}` to its `ok` read or M1 mutation envelope, binding the exact Task/version displayed by both reads. `task_workflow=null` means the authorized Task has not opted in. Do not change `clued_task_owner_detail_v1`'s existing exact response schema. UI reads both RPCs with the existing Owner/token/target/generation guards and ignores late responses after any account or Task change; mismatched Task/version views disable writes until refresh. Acceptance has a system acceptance ID as its primary target and the exact Task as source; it does not invent a committed Task version. Canonical completion binds the Task ID and actual base/committed versions through its Record mutation Receipt.

Workflow projection:

```text
{contract,goal_version,definition,delivery_refs,deliveries,
 completion:{ready_for_acceptance,eligible,reasons,completion_digest,
             owner_accepted,acceptance_receipt_id?}}
```

Each authorized delivery exposes only `{deliverable_id,job_id,status,reason?,connection_id?,artifact_id?,artifact_version?,path?,provider_file_id?,provider_file_version?,sha256?,size?,mime_type?,receipt_id?,registration_receipt_id?,verified_receipt_id?,verified_digest?,link?,verified_at?,verification_scope?}`. `receipt_id` is settlement; `registration_receipt_id` is the actual current Artifact registration Receipt; `verified_digest` is an immutable proof digest, not its private payload. Status is `verified | pending | unknown | stale | rejected`. It never returns issuer hashes, token/lease keys, mutation content or raw private authority snapshots.

Candidates are at most the latest 30 Owner-authorized Storage file jobs in the exact Task Project (or authorized Owner Projects for a Global Task), sorted by creation time, with `{job_id,label,path,state}` only. UI lets the Owner select a filename instead of requiring an internal UUID. Foreign-owner/project jobs cannot leak through candidates or direct binding. Agent refs additionally require current read authorization to the referenced scope; context write does not grant a new Storage effect.

## File proof and completion

Qualification reads existing `storage_jobs_v1` → `resource_center_mutations_v1` → immutable `verified_result_v2` and its digest/Receipt → committed settlement/registration → currently active exact Artifact/profile/path/Decision. It compares Owner, scope, Job/intent/request digests, proof hash, all relevant committed Receipt identities, exact provider file ID/version/path, file target, size/SHA and any required MIME. Existing Storage locks/source-row locks serialize completion with registry change; no lock is held over network I/O.

Because M1 already holds the Owner currentness/Task lock, qualification uses nonblocking `pg_try_advisory_xact_lock` for the existing Storage root fence and `FOR SHARE NOWAIT` for source rows, avoiding an inverse blocking dependency on Storage's root-first order. The existing Storage permission evaluators run with a bounded 100ms lock timeout, restored afterwards, so a busy evaluator also fails closed without creating a blocking inverse dependency. Busy sources remain unknown/ineligible; acquisition succeeds only for a stable transaction snapshot. Actual two-client tests verify prompt refusal during a held registry lock and refusal of the changed version afterwards.

Only trusted persisted `clued.storage-create-verified/2`, `/3` and `clued.storage-replace-verified/1` file-verification contracts carrying verified content size/SHA can qualify. Existing `clued.storage-adopt-verified/1` lacks content SHA/size and is explicitly unsupported for file-integrity completion; adopting a file proves registration only. Directory/trash/cancelled/failed jobs cannot prove file delivery. `queued/started/uncertain`, missing/corrupted proof, missing settlement/registration, stale Artifact/version/path, revoked authority, unknown currentness, failed MIME/SHA/location criteria and missing required items keep completion ineligible. The version's proof is reused; caller links or success text do not manufacture it. Missing optional delivery remains visible without satisfying a required condition.

Every qualified delivery explicitly reports `verification_scope=persisted_storage_and_current_registry` and persisted `verified_at`. This proves successful archival at that verification boundary and the currently registered exact version. It is not a fresh Google Drive head observation; external changes not observed by Clued remain outside this claim. Legacy text `/2` verification lacks verified MIME and reports MIME unknown; an exact MIME expectation stays ineligible. Rendition/export is never substituted for raw-byte identity.

`completion_digest` binds the current goal version, revalidated inputs and ordered delivery qualifications (including exact Artifact/version/verification and settlement Receipts), excluding the acceptance row itself. Native acceptance and completion must submit that exact digest. Goal, file, input or authority changes invalidate it. On **every transition to completed**, the trigger first requires a **fresh pending Owner-matched M1 `record_mutation` Receipt distinct from `OLD.receipt_id`**, then checks the old active Task's actual currentness and the new definition's qualification. This is normative for generic M1, Native and direct table writes: a direct update reusing an old Receipt cannot complete the Task or avoid its M1 Event/Receipt. Source-row locks serialize qualification with registry changes. Machine mode completes only when file checks pass; owner mode additionally needs an actual Native acceptance of the exact digest. Native owner mode may acknowledge declared-input uncertainty but cannot waive missing required files, invalid file proof, stale versions or unsupported business/physical results.

To bind a pending Receipt to the actual mutation, a bounded private immutable completion-admission row records `{receipt_id,transaction_id,owner_id,task_id,base_record_version,scope,operation:"close",target_lifecycle:"completed",request_sha256}`. A revoked private helper creates it **only inside the existing M1 core after successful row/CAS/lifecycle checks and before that canonical UPDATE**; it recomputes the exact invocation's M1 request hash and verifies the pending Receipt's Owner, Binding and hash. An exact anchor-count patch fails migration closed if the upstream core differs. Failed close/subtransaction rolls admission back. The trigger requires this matching admission in the **same current PostgreSQL transaction** as the fresh pending Receipt and the exact OLD Task/version/scope. A pending Receipt for another Task, operation, CAS or earlier transaction is insufficient. No caller-writable GUC or flag is a sole authority. The private table has RLS, no external grants, and rejects updates/deletes; it stores audit metadata only and does not add a Task/intent body.

## Required verification

Use the full current migration chain in an isolated database. Load this migration through the actual production publisher's CSV COPY, LF reconstruction, MD5 validation, single PL/pgSQL EXECUTE and schema-migration ledger transaction; compare the recorded SQL byte-for-byte. Cover: legacy Task close unchanged; successful machine file delivery/close with Event+Receipt; Native owner acceptance/close; Agent acceptance forgery; direct-table and generic-close bypass; marker removal/null/replace; malformed/null schema; body/scope/input change invalidation; stale Record CAS/goal/digest; missing/queued/cancelled/corrupted/mismatched proof; Artifact move/version/revoke; MIME unknown and mismatch; cross-owner/project Job/Artifact/Record input; declared-input machine rejection and explicit owner limitation; Native delegated/service/anonymous rejection; `expected_owner_id` account switch; candidate cap/no private-field leakage; idempotent mutation/acceptance replay; row-lock race with registry changes; actual approved Agent read+inspect positive fixtures and read revocation/client/root/read-class deny/inspect-capability withdrawal masking across list/search/mutation; Global Task cancel/archive after source read/Project removal while completion still fails; 16 retired IDs → 16 new IDs → rebind → completed without losing current-goal refs or M1 history; all new private tables RLS/revokes and narrow public execution grants.
