- 已定结构（Owner 2026-10-04 选择，记录在 Task `4b9627a6`）：预设角色 + 高级勾选，两种模式共用一套底层。

## 1. 现在哪里复杂

2026-10-04 一天之内遇到的问题：

1. **新项目不在连接里。** 授权页默认全选，但只能选连接当时已有的项目。之后新建的项目（例如 M2）不在任何已有连接里，Agent 一写就被拒。
2. **被拒时看不出缺什么。** 网关拒绝只返回一个裸的 HTTP 403（`insufficient_scope`），数据库拒绝的细节放在 403 的 `data` 里，很多 Host 会丢掉它。Agent 只能猜缺的是哪个 scope、哪个项目、哪个动作。
3. **发布要批两到三次。** 迁移和部署是两个动作，各批一次；迁移授权还要按迁移文件写资源，按提交写会对不上（运行 37203380144），Owner 又多批了一次。
4. **授权页对不上编号。** "我的授权"只显示动作和范围，Agent 说的编号（如 `a0e3b847`）在页面上找不到。
5. **令牌轮换后要手动同步。** 轮换 Headless 连接时角色会立即转到新连接，但 GitHub 里存的旧令牌不会自动更新，CI 准入因此停了两轮。

问题不在于某一层权限是否合理，而在于叠加之后，Owner 和 Agent 都得记住太多格子。

## 2. 原则：两种模式，底层一套

- **简单模式（默认）**：选一个预设角色。
- **高级模式**：现有的逐格勾选（上下文 × 动作），默认收起。
- **底层只有一套**：预设角色只是"打包好的勾选"，落到数据库仍是 `authorization_entries_v12` 里的同样条目。检查、撤销、收窄、审计都走现有路径，PR #539 的实现作为底层原样保留。
- **不允许出现两套语义**：同一个连接在两种模式下看到的权限必须完全一致；高级模式改过的连接，简单模式显示为"自定义"。

## 3. 改动

### 3.1 预设角色

| 角色 | 展开为 | 适用 |
|---|---|---|
| 只读 | 所选范围内每个上下文：读取 | 查资料、做汇总的 Agent |
| 项目开发者 | 所选项目：读取、新增和修改、关闭和归档、恢复；个人记忆（Global）：读取 | 在某个项目里干活的 Agent |
| 全部 | 个人记忆、个人资料、所选项目：全部动作 | Owner 自己的主力 Agent |

范围有两种选法：

- **指定项目**：和现在一样，落成具体的 `project:<id>` 条目。
- **我的全部项目（含以后新建的）**：落成一条通配条目 `project:*`，检查时按"该项目属于 Owner 本人"展开。这条直接解决问题 1：以后新建的项目不用再补权限。

连接的授权页改成：先选角色和范围，"高级"里才显示现在的逐格勾选。连接管理页（`/oauth/connections`）显示每个连接的角色名，可以"换角色"（收窄直接生效；放宽仍走 Owner 在确认页批准）。

### 3.2 被拒时直接说该申请什么

- 权限拒绝不再是裸 403，改为 HTTP 200 的工具错误结果（`isError: true`）。这样 Host 不会丢掉内容，与现有的规则拒绝走同一条路。
- 结果里固定包含：
  - `error_code`：沿用现有错误码（`insufficient_scope`、`binding_not_authorized`、`resource_action_not_authorized`）；
  - `missing`：缺的上下文和动作，例如 `{"context": "project:<id>", "action": "write"}`，以及项目名；
  - `suggested_request`：可以直接原样提交的 `clued_owner_request` 参数（`action: connection.permission` 和 `resources`）；
  - `suggested_role`：能覆盖这次操作的最小预设角色，例如"M2 项目开发者"。
- `connection.permission` 申请除了逐项写 `permission:<context>/<action>`，也可以写角色，例如 `permission:project:<id>/developer`。确认页把角色展开成具体的勾选给 Owner 看，批准后仍落成同样的条目。
- 合同 §6.7 随之简化为一句：被拒时把结果里的 `suggested_request` 原样提交，把返回的链接交给 Owner。

### 3.3 发布一次批准（Task `23045c17`）

- 一个申请可以包含多个动作，针对同一个提交：迁移（每个迁移文件一项资源）和部署（提交一项资源）。
- 确认页一次批准，为每个动作分别生成授权；发布门口仍按动作各自扣减，每次使用仍有独立回执。
- 发布流程在没有授权时自己开的申请，也改为一次列出这次要用的全部动作和资源。
- 顺带修正合同 §6.6：迁移授权的资源是 `repo:<owner>/<name>/<commit>/apps/clued-cloud/supabase/migrations/<file>`，不是提交本身。

### 3.4 授权页显示编号

"我的授权"（`/grants`）每条授权显示：授权编号前 8 位、对应申请编号前 8 位、关联 Task（有的话）、发起的连接名。等待中的申请同样显示申请编号。Agent 给 Owner 的链接和编号与页面一一对应。

### 3.5 令牌轮换提示要同步的位置

- 带角色的 Headless 连接（`ci-admission`、`release-door`）在连接管理页标出它在 GitHub 里对应的位置：
  - `ci-admission` → 环境 `clued-admission` 的 secret `CLUED_ADMISSION_CLUED_TOKEN`；
  - `release-door` → 环境 `clued-release` 的 secret `CLUED_RELEASE_TOKEN`。
- 轮换成功页把新令牌和"请更新到哪个 secret"放在一起显示，并提示旧令牌 60 分钟后失效。
- 准入检查读到空令牌或角色不符时，失败信息直接写出应该更新哪个 secret，而不是只报 `admission_binding_required`。

## 4. 安全边界怎么变

| 改动 | 变宽的地方 | 守住的地方 |
|---|---|---|
| 预设角色 | 一次授出的格子更多 | 角色只是打包好的勾选，Owner 在授权页看到展开后的全部内容再批准；撤销、收窄照旧 |
| 全部项目（含以后新建） | 以后新建的项目自动包含在内 | 只有 Owner 主动选这一项才会出现；只覆盖 Owner 本人的项目，不含别人共享给你的项目；连接管理页明确标出"含以后新建的项目" |
| 被拒时给出建议申请 | Agent 更容易发起申请 | 申请本身不授予任何东西，仍须 Owner 在已登录的确认页批准 |
| 角色写进申请 | 一次申请可以覆盖多个动作 | 确认页展示展开后的每一项，批准的就是展示的内容 |
| 发布一次批准 | 一次点击生成多个授权 | 每个授权仍限定在同一提交、各用一次、独立回执；迁移仍逐个列出文件 |
| 授权页编号、令牌提示 | 无 | 只增加显示，不改变权限 |

## 5. 保持不变的部分

- Owner 批准仍只能在 Owner 本人已登录的 Clued 页面完成，Agent 转述的话不算批准。
- 连接不能自己给自己加权限；连接权限申请仍是"只批这一次、只给发起的连接"。
- 数据库层的逐条检查（`authorization_entries_v12`）仍是唯一的强制边界，网关预检只是粗筛。
- 生产迁移和部署仍须 Owner 授权，仍经发布 workflow 执行。
