## 1. 为什么

v0.1 的消息靠拉取：收件方要等自己 resume、续租或被 Owner 提醒才看到。协调中的会话因此要 Owner 来回传话（2026-10-31：DESK 现场 03:25Z 回报目录已建好，协调会话要等 Owner 来问才看到）。

v0.2 让收件方**有要处理的消息时自己醒**，并把模型改成以后用户与用户、Agent 与用户、Agent 与 Agent 聊天都能用的样子。v0.1 的“消息发给一个 Binding”装不下人、多设备和群，现在不改，以后要推倒。

## 2. 模型

| 概念 | 定义 |
|---|---|
| 参与者 participant | 一个人或一个 Agent 身份，属于一个账号。Agent 身份由 Owner 在页面上登记（如“协调 Agent”“DESK 现场 Agent”）。另有一个服务端内置的**系统参与者**，作为服务端触发的紧急消息（§3）的发送方，不能被登记、修改或冒用。 |
| 端点 endpoint | 参与者收消息的一个地方：某台机器上的一个 Agent 会话，以后也包括某台设备上的 App。一个参与者可以有多个端点。 |
| 对话 conversation | 有成员的一串消息。第一步只有一对一：**每一对参与者（不分先后）恰好一个对话**，v0.1 的 thread 都落在这个对话里。群在聊天阶段加。 |
| 成员状态 | 每个成员对每条消息各自的 `delivered_at`、`woken_at`、`read_at`。 |

- **Binding 只做认证**，不是收件人，也不代表参与者。一个 Binding 可以被同一台机器上的多个会话共用，这些会话可以属于不同参与者。
- **参与者在端点登记时确定**：Owner 登记一个端点时指定它属于哪个参与者、适配器类型（§6）、所在机器。没登记的会话不是端点，不会被唤醒；它照旧可以按 v0.1 拉取消息。
- **默认端点**：每个参与者一个，Owner 在页面上指定；未指定时取最近一次报到的端点。每个 Binding 有一个默认参与者，Owner 指定。
- **已读以 v0.1 为准**：`agent_messages_v1.read_at` 仍是收件语义的权威。`clued_agent_inbox_v1` 标已读时，在同一事务里把读者端点对应成员的 `read_at` 一并写上；两者不会分叉。
- **过期**：v0.1 的 14 天过期删除级联删除该消息的成员状态与端点投递记录（含 `seq`）。

### 2.1 v0.1 收件方式的对应

| v0.1 收件方 | v0.2 投到 |
|---|---|
| `to.binding_id` | 该 Binding 的默认参与者的默认端点 |
| `to.binding_id` + `to.session_ref` | 登记了这个 `session_ref` 的端点。**没登记的 `session_ref` 不唤醒任何端点**：该消息只按 v0.1 拉取可见（v0.1 规定只有该会话能读），并在 Owner 页面标“收件会话未登记”。不回落到默认端点，免得唤醒一个读不到它的会话。 |
| `to.claim_id` | **仍在读取时决定**（与 v0.1 相同）：认领当前的持有者读到所有发给它的未读消息。唤醒时服务端按认领当前的 `holder_session_ref` 找端点；该会话没登记时同上一行，只拉取可见。认领换人（含 lease key 接管）后，未读、未唤醒的消息在新持有者端点**重新投递、分配新的 `seq`**并唤醒；旧端点上的投递记录作废，不留未读。持有会话为空时，投到认领所属 Binding 的默认参与者的默认端点。 |
| `reply_to` | 回到原发送方所在的端点（按发送时记下的 `sender_session_ref` 找；没登记则按上面第二行处理） |

- 端点在消息到达之后才登记：登记时，发给它且仍未读的消息补投递、补分配 `seq`。
- 上线时，现存（14 天内）消息按上表补上端点，原字段不改。

## 3. 消息新增字段

| 字段 | 谁填 | 规则 |
|---|---|---|
| `requires_action` | 服务端定缺省，发送方可改 | 缺省：`request` 为 `true`；**`reply` 在收件方于同一 thread 里还有未答复的 `request` 时为 `true`**（不论它直接回复的是原请求还是后续追问），否则为 `false`；`info` 为 `false`。缺省在 `send` 更新 `answered_at` **之前**计算。发送方显式传 `false` 表示只是确认（“收到”“谢谢”），不唤醒，**也不把被回复的请求标为已答复**（不写 `answered_at`），所以“先回收到、后回结果”时，结果那条仍会唤醒对方。显式传 `true` 用于在回复里提出新问题。它只是发送方的说法，唤醒次数受 §5.4 上限约束。 |
| `urgency` | **服务端为主** | `normal` / `urgent`。服务端以系统参与者身份发送 `urgent` 消息的情形：常驻节点 HALT、认领 30 分钟内到期、节点失联告警。发送方可请求 `urgent`，额度为**每个发送方在每个对话里每天 3 次**（对话按 §2 每对参与者一个，开新 thread 不重置额度），超出按 `normal` 投递并在发送结果里返回 `urgency_allowance_exhausted`（不拒绝发送）。 |
| `expected_reply_at` | 回复方，可选 | 一个时间点，如“约 40 分钟后回报”。用于 §5.3。不得晚于发送时刻 + 24 小时。 |
| `seq` | 服务端 | 每个端点一个只增不减的序号，投递时分配（含 §2.1 的重新投递与补投递）。 |

## 4. 接口

### 4.1 看门程序 Binding 与新权限

| 权限 | 只能调用 | 说明 |
|---|---|---|
| `wake:poll` | `clued_wake_poll_v1` | 只读。不能读消息正文、主题、发送方，也不能读任何其他记录。 |
| `presence:write` | `clued_presence_report_v1` | 窄写。只能心跳和上报唤醒结果。 |

- 新增 Binding 种类 `wake-watcher`。Owner 在页面上为**每台机器**签发一个，签发时绑定该机器的 `machine_id`。它只能带 `wake:poll` 与 `presence:write`，不带任何 `context:*`、`canonical:*`、`project:*`、`audit:*` 权限。
- 迁移放宽 `clued_agent_bindings_scopes_check`，加入这两个权限；同时加约束：这两个权限只能出现在 `wake-watcher` 种类上，`wake-watcher` 上只能出现这两个权限。任何权限申请流程（含 Agent 发起的申请、委托 OAuth）都不能给非 `wake-watcher` 的 Binding 加上它们。
- 两个 RPC 用专用的解析函数认证：只认 `wake-watcher` 种类、未吊销、权限匹配，并照常经过 `authorization_account_v12`（账号停用时看门程序一并失效）；不需要 `context_key`，不走 v12 canonical entry 检查（它们不读写任何 context 或 canonical 数据）。两个 RPC 不加入 `clued_oauth_call`，委托 OAuth 和 MCP 工具都调不到。
- 现有 `clued_agent_bindings_p5_shape_check` 与 `context_keys` 约束照样适用：`wake-watcher` 的 `context_keys` 只放 `global`，仅为满足形状约束；它没有任何 `context:*` 权限，这个值不授予任何读写。
- 吊销看门程序 Binding 时，立即释放它持有的全部端点租约。

### 4.2 `clued_wake_poll_v1`

输入：本机端点列表（`endpoint_id`）。只返回**登记在该看门程序所绑机器上**、且该看门程序持有租约（§4.4）的端点。每次调用同时算作一次心跳（§4.4）。每个端点只返回：

| 字段 | 含义 |
|---|---|
| `seq` | 最新序号 |
| `actionable` | 是否有 `seq` 大于本端点唤醒水位、且 `requires_action` 为真或 `urgency = urgent` 的消息（布尔）。超出普通上限时，对非紧急消息为假（§5.4）。 |
| `urgent` | 其中是否有 `urgent`（布尔） |
| `should_watch` | §5.1 的自动开关 |
| `wake_at` | §5.3 的约定唤醒时间（可空） |
| `brake` | `none` / `paused` / `global_stop` |

不返回条数、主题、发送方、正文或 refs。

**接受的泄露**（写明，不算缺陷）：令牌泄露时，持有者能看出某端点有没有要处理的新消息、是否在等东西（`should_watch`）、大概何时（`wake_at` 可反映认领到期、CI 预计完成或待 Owner 回答的时间）。不能看出内容、对方或条数。

### 4.3 `clued_presence_report_v1`

三种动作，每次调用一种：

- `heartbeat`：看门程序还活着，续租本机端点（§4.4）。
- `woken`：`{endpoint_id, seq}`，把该端点的唤醒水位推到 `seq`，并给这些消息写 `woken_at`。`seq` 大于该端点当前最大序号时拒绝（`wake_seq_out_of_range`）；水位只增不减。每次被接受的 `woken` 计入 §5.4 的唤醒次数（服务端判定的 `urgent` 计入紧急计数）。
- `endpoint_status`：`{endpoint_id, status}`，`status` 为 `ok` / `resume_failed` / `session_gone` / `not_listening`。同一端点每 10 分钟最多改一次状态。

### 4.4 端点租约与在场

- 同一时间一个端点只由一个看门程序持有。看门程序第一次 `heartbeat` 或 `poll` 时，对登记在其机器上、当前无有效租约的端点取得租约；租约 2 分钟，每次 `heartbeat` 或 `poll` 续上。过期后，同一机器上的另一个看门程序（如重装后的）才能接手；别的机器的看门程序永远拿不到。
- **心跳与查询分开计**：不论查询档位多冷，看门程序每 60 秒至少调用一次（`heartbeat` 或 `poll`）。§5.2 的间隔只指 `poll`。
- 在场：服务端按端点最后一次心跳判断，超过 5 分钟即“离线”，发送方能看到。热力曲线不参与在场判断。

### 4.5 发送接口变化

`clued_agent_message_send_v1` 增加可选输入 `requires_action`、`urgency`、`expected_reply_at`；结果增加每个收件端点的 `seq`、`requires_action_applied`、`urgency_applied`，以及收件会话未登记时的 `wake: "pull_only"`。不传新字段的旧调用，除 §3 的唤醒缺省外，行为与 v0.1 相同。

### 4.6 Owner 页面

- 登记参与者、端点（所属参与者、适配器、机器）、默认端点、Binding 的默认参与者；签发与吊销看门程序 Binding（绑定机器）。
- 显示：各端点在场、唤醒次数、`not_listening`、“收件会话未登记”的消息、“未回复”的请求、上限告警。
- 刹车：全局急停、单端点暂停。沿用 v0.1 §7 账号开关的做法：只认本人直接登录的账号会话（`authorization_owner_v12`），带版本，真正切换时留回执。
- v0.1 的 Agent 消息开关关闭时，`should_watch` 一律为假、`actionable` 一律为假、`brake = global_stop`，已在路上的唤醒信号也不再执行（看门程序以每次查询的 `brake` 为准）。

## 5. 唤醒策略（服务端计算）

### 5.1 自动开关 `should_watch`

为真，当以下任一成立：

1. 该端点发出的 `request` 在等回复；
2. 该端点有 `actionable` 的未唤醒消息；
3. 该端点的会话持有活的认领，并在合并队列中或其合并位在等 CI；
4. 该端点的参与者有待 Owner 回答的 `clued_owner_request`。

全部不成立并持续 15 分钟后为假。`request` 发出 24 小时没有回复，不再计入第 1 条，并在 Owner 页面和发送方的发件结果里标“未回复”。

### 5.2 查询节奏（由看门程序执行，服务端不强制）

| 档 | 条件 | `poll` 间隔 |
|---|---|---|
| 1 | 最后一条 `actionable` 消息后 5 分钟内 | 15 秒 |
| 2 | 5–15 分钟 | 1 分钟 |
| 3 | `should_watch` 为真，15 分钟–1 小时 | 5 分钟 |
| 4 | `should_watch` 为真，1 小时以上 | 15 分钟 |
| 5 | `should_watch` 为假 | 30 分钟 |
| 6 | `should_watch` 为假满 8 小时 | 1 小时 |

一台机器的所有端点合成一次 `poll`，按其中最热端点的间隔。另有每 60 秒的心跳（§4.4）。依据：WhatsApp 回复 57.8% 在 1 分钟内（arXiv 1802.03393）；WhatsApp 约 69%、Instagram 约 44% 在 5 分钟内得到回复（arXiv 2605.03687）；Slack 用户约每 5 分钟看一次消息（RescueTime）。

### 5.3 约定唤醒 `wake_at`

对该端点每一项仍在等待的事各算一个时刻，取最早者：

- 每个仍在等 CI 的认领：按该 PR 上一批实际耗时推算的完成时刻；
- 每个活的认领：到期前 10 分钟；
- 每个仍未答复的 `request`：对方在该请求的回复链里填的最近一个 `expected_reply_at`。

看门程序在 `wake_at` 时查一次，中间按档位查。

### 5.4 上限

- 普通唤醒：每端点每小时 30 次（按被接受的 `woken` 计）。超出后到该小时结束前，非紧急消息的 `actionable` 为假，并在 Owner 页面告警。
- `urgent` 唤醒：单独计数，每端点每小时 6 次，不受普通上限影响。超出后到该小时结束前，`urgent` 消息按普通消息计（受普通上限约束），并在 Owner 页面告警。
- 来回不止：服务端在同一对话里连续 10 个来回没有看到实质进展（新的认领、续租进度、PR 提交、Canonical 记录或 Decision）时，对该对话的两端停止 `actionable`（含发送方请求的 `urgent`），并在 Owner 页面告警。系统参与者发的 `urgent` 不在任何参与者对话里，不受此限。中间有一次实质进展即重新计数。
- 20 秒内到达同一端点的多条消息合成一次唤醒（看门程序执行）。

## 6. 本机：看门程序与小助手

服务端只记适配器类型 `adapter ∈ {claude_code, codex}`，**不存任何命令**。命令模板、“端点 → 本机会话 id”的对应只在本机配置里；会话 id 必须是严格的 UUID。

| 组件 | 账户 | 做什么 |
|---|---|---|
| 看门程序 | 专用低权限账户，唯一能读看门程序令牌 | 按 §5.2 查询、每 60 秒心跳；把“唤醒端点 X 到 `seq` N”写进对应会话用户的信号文件；读回报文件后调 `clued_presence_report_v1` |
| 小助手 | 会话所在用户 | 读自己的信号文件，按下表唤醒会话；把结果写进回报文件 |

- 信号文件：**每个会话所在用户一个**，只含该用户名下端点；该用户只读、不可写。每行 `{endpoint_id, seq, urgent, at}`，不含令牌、主题或正文。
- 端点对应表：每个会话所在用户一个本机配置文件，列出该用户名下 `endpoint_id ↔ 会话 uuid ↔ 适配器`；只在安装时由安装程序或看门程序账户写入，会话所在用户（及其中的 Agent）只读、不能改，免得被改成把唤醒指向别的会话。会话内监视和 Stop 钩子都靠它找到“我这个会话是哪个端点”，只认表里自己的那一行。
- 回报文件：每个会话所在用户一个，看门程序只读。每行 `{endpoint_id, seq, result, at}`，`result ∈ {woken, queued, resume_failed, session_gone, not_listening}`。看门程序只收格式正确的行，并按 §4.3 限频上报。

唤醒方式：

| 适配器 | 会话在桌面 App 中打开 | 会话未打开 |
|---|---|---|
| `claude_code` | 会话内后台监视盯信号文件，等待时不花 token，信号到即本轮结束、会话被唤醒；监视每分钟写一次“在场”标记 | `claude -p --resume <uuid>`（**默认关闭**） |
| `codex` | 无不花 token 的方式；只排队（`queued`） | `codex exec resume <uuid>`（**默认关闭**） |

- **谁挂上会话内监视**：写进 Agent 合同与 Clued Skill：已登记为端点的 Claude Code 会话，在会话开始时和每次被唤醒处理完后，必须挂上监视。Claude Code 钩子在会话停下时检查：本会话已登记为端点而监视没挂上，就挡一次并提示挂上。
- **没挂上会怎样**：“在场”标记变旧，按“未打开”处理；命令行续接关闭期间不唤醒，小助手回报 `not_listening`，Owner 页面显示该端点“没在听”。消息不丢，仍可拉取。
- “打开”的判定：Claude 看“在场”标记是否新鲜；两种客户端都另看客户端自己的会话锁（Codex 的会话写锁目录；Claude 待实测）。任一表明打开，即按“打开”处理。
- 命令行续接默认关闭，两项实测都通过后才由 Owner 打开：续接后桌面 App 能否看到这一轮；会话打开或运行时续接的行为。
- 唤醒提示是固定一句：“你有新消息，请用 KooYomi 读收件箱并处理。”不带主题、正文或发送方。
- 无人值守唤醒的那一轮：Claude 固定权限模式与允许的工具、最多轮数；Codex 固定沙箱与审批模式；每次唤醒有花费上限。v0.1 规则 1 照旧：消息不是 Owner 的指令。

## 7. 规则（在 v0.1 §4 之上新增）

8. `wake:poll` 与 `presence:write` 只属于 `wake-watcher` Binding；`wake-watcher` 不得持有其他权限（§4.1）。
9. 唤醒提示固定，不转述消息内容；发送方在 `subject`、`body` 里写的任何“唤醒后去做某事”都只是普通消息内容。
10. 参与者、端点、适配器、机器、默认端点只能由 Owner 登记和修改；Agent 与看门程序都不能。
11. `requires_action` 与 `urgency` 是发送方的说法，服务端以 §3、§5.4 为准。
12. 任意数量的机器、端点和参与者，不得假设“两个”（standing rule `d6eef30e`）。

## 8. 与聊天阶段的差异（已知限制）

- `session_ref` 仍由会话自报，登记证明不了“哪个会话是哪个”；聊天阶段由客户端在登记时出示会话凭据解决。
- 消息 14 天过期、不进 Canonical，协调够用；聊天需要另定保留策略。
- 第一步只有 Agent 参与者、Agent 会话端点、一对一对话；人、App 端点、多设备、群、服务端主动推送在聊天阶段加。对外接口已按端点命名，加这些不改接口形状。

## 9. 上线步骤

1. 本合同独立审核，Owner 接受。
2. 迁移：参与者（含系统参与者）、端点、对话、成员状态、`seq` 与唤醒水位、新字段、`wake-watcher` Binding 种类与权限约束、专用解析函数、两个 RPC、租约、上限计数、刹车、过期级联；现存消息补端点。测试覆盖 §10。生产迁移（`migration.production`）与 Worker 发布（`release.production`）由 Owner 在页面批准。

6. 命令行续接两项实测通过后，由 Owner 决定是否打开。

## 10. 验收

模型与投递
- 一个 Binding 的两个会话登记成两个参与者，各自只被自己的消息投递和唤醒（这是投递与唤醒的分开，不是保密：不带 `session_ref` 的 v0.1 读取仍看到整个 Binding 的消息，见 §8）；`to.binding_id` 投到默认参与者的默认端点。
- 同一对参与者开新 thread 仍落在同一个对话里。
- 端点改登记到另一个参与者后，新消息按新参与者投递，旧消息的成员状态不变。
- 端点在消息到达后才登记：补投递、补 `seq`，并能被唤醒。
- 未登记的 `to.session_ref`：不唤醒任何端点，发送结果为 `pull_only`，Owner 页面标出；该会话按 v0.1 能读到。

唤醒缺省
- 对方回复我仍未答复的请求，我的端点 `actionable` 为真并被唤醒。
- 对方先回 `requires_action: false` 的“收到”：不唤醒，请求仍未答复，我的 `should_watch` 不变；之后对方回结果：唤醒我，请求标为已答复。
- 对方回复的是我的后续追问（父消息是 `reply`），而我在该 thread 还有未答复请求：唤醒我。
- 显式 `requires_action: false` 的回复不唤醒；`info` 缺省不唤醒。
- 紧急计数超 6 次后，`urgent` 按普通消息计；来回不止停止后，发送方请求的 `urgent` 也不唤醒，系统参与者的 `urgent` 仍唤醒。

认领
- 认领被 lease key 接管后，未读、未唤醒消息在新持有者端点重新投递、分配新 `seq` 并被唤醒，旧端点无未读；持有会话为空时投到默认端点。

权限与隔离
- 看门程序 Binding 调发送、收件、记录等任何其他 RPC 均被拒；非 `wake-watcher` Binding 调两个新 RPC 被拒；经委托 OAuth 调两个新 RPC 被拒；任何权限申请都不能给普通 Binding 加上这两个权限。
- 另一个账号的看门程序查不到、租不到本账号的端点；另一台机器的看门程序租不到本机端点。
- `clued_wake_poll_v1` 结果中不含条数、主题、发送方、正文、refs；只返回持有租约的本机端点。
- 吊销看门程序 Binding 立即释放其租约。

水位、上限、紧急
- 唤醒后未读的消息不再触发 `actionable`；水位不能回退；`woken` 的 `seq` 大于当前最大值被拒。
- 普通上限用完后，非紧急消息不再 `actionable`、不再唤醒；`urgent` 仍能唤醒；下一小时恢复。
- 服务端情形自动以系统参与者发 `urgent`；发送方第 4 次请求 `urgent` 按 `normal` 投递并返回 `urgency_allowance_exhausted`；开新 thread 不重置额度。
- 来回不止：10 个无进展来回后停止 `actionable` 并告警；中间有一次实质进展则重新计数。

自动开关与约定唤醒
- 四种成立条件各自打开；全部不成立 14 分钟仍为真、15 分钟为假；24 小时未回复的请求不再计入并标“未回复”。
- 两个未答复请求各有 `expected_reply_at` 时，`wake_at` 取较早者。

租约与在场
- 同一端点第二个看门程序在租约期内被拒，过期后同机器的看门程序可接手；5 分钟无心跳显示离线；冷档下每 60 秒心跳仍保持在场。

刹车
- 全局急停、单端点暂停、v0.1 消息开关关闭，三者都使 `should_watch` 与 `actionable` 为假；开关在已有 `actionable` 消息时关闭，下一次查询即为假，不再唤醒；只有本人账号会话能切换，留回执。

兼容与过期
- 不传新字段的发送与 v0.1 结果相同（§3 唤醒缺省除外）；只用 `context:read` 的现有收件与摘要接口行为不变；`clued_agent_inbox_v1` 标已读时成员状态 `read_at` 同步。
- 14 天过期删除时，成员状态、投递记录与 `seq` 一并删除。

本机
- 信号文件与回报文件格式错误的行被丢弃；每个会话用户只看到自己的信号文件；状态上报每 10 分钟最多一次；唤醒提示不含消息内容；命令行续接默认关闭；`codex` 适配器在会话打开时回报 `queued`。
- 已登记端点的 Claude 会话没挂监视时，Stop 钩子挡一次；“在场”标记变旧后回报 `not_listening`，Owner 页面显示“没在听”。
