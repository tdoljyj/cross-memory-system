# Information Flow native write surfaces v0.1

Moved verbatim from the root `AGENTS.md` "Canonical writes" section so that agent operating rules and product write-surface specifications are maintained separately. The root `AGENTS.md` links here; this text keeps the same normative force it had there. Add later Information Flow stages here, not to `AGENTS.md`.

- Information Flow candidates (`development/contracts/information-flow/M0DCloseout.v0.1.md`): `clued_intake_submit` / `clued_user_intake_submit`, `clued_intake_withdraw` / `clued_user_intake_withdraw` and `clued_knowledge_propose` / `clued_user_knowledge_propose` write only isolated `clued_private` candidate rows through the M1 receipt/idempotency core (`intake_submit`, `intake_withdraw`, `knowledge_propose`; candidate rows use row-version CAS). A candidate is never a Canonical Record or current truth.
- Information Flow promotion (S3): `clued_candidate_confirmation_issue_v1` (step 1), `clued_candidate_promote_v1` (step 2) and `clued_candidate_reject_v1` are Native account-session RPCs only (`authenticated`, `authorization_owner_v12`; REST `POST /v1/intake/{id}/confirmation|promote|reject` and `POST /v1/knowledge/candidates/{id}/confirmation|promote|reject`; never an MCP tool, OAuth case or Binding). Promote and reject are receipt-core families `candidate_promote` / `candidate_reject` with candidate row-version CAS (`base_version` = candidate `version`). Issuing writes no Receipt: it stores only the hash of a single-use token (5-minute TTL, session authenticated within 15 minutes) bound to user, tier, candidate id and version, input digest, Native choices, pre-allocated Record id, session and the confirmation-view digest of the final Record body. Promotion consumes that token in the same transaction as the Record create, which goes only through `record_mutation_with_terminal_guard` (inner `record_mutation` Receipt; Record CAS is the M1 `base_version`), and records provenance in `clued_private.candidate_promotions`. Account-session writes through `/v1/records` and direct-session `/v1/decisions/supersede` also write `clued_private.native_write_markers`; `human_confirmed` is true only from those markers for the exact version (no backfill). Evidence withdrawal (S5) is the same kind of receipt-core family; see below.
- Information Flow Context Policy (S4): `clued_context_policy_confirmation_issue_v1` (step 1, REST `POST /v1/context/policies/confirmation`) and `clued_context_policy_accept_v1` (step 2, REST `POST /v1/context/policies`) are Native account-session RPCs only (`authenticated`, `authorization_owner_v12`; never an MCP tool, OAuth case or Binding). Acceptance is the receipt-core family `context_policy_accept`; its CAS is the policy lineage `base_policy_version` (the active `policy_version` for the `task_class`, 0 for a new lineage) and the approving Decision's M1 `base_version`. Issuing writes no Receipt and stores only the hash of a single-use token in `clued_private.native_confirmation_tokens` (5-minute TTL, session authenticated within 15 minutes, bound to user, action, `task_class`, lineage version, session and the view digest over the normalized `clued.context-policy.v1` document and the final Decision body). Acceptance writes the approving Decision only through `record_mutation_with_terminal_guard` (`binding_id=null`, `authority=user_explicit`), its `native_write_markers` row and the `clued_private.context_policies` row in one transaction. A policy is usable only while that exact Decision version is the current version, is CURRENT and is Native-marked; any update, supersede, close or shadowing fails compiles closed until a new Native acceptance. Compiles (`clued_context_pack` / `POST /v1/context/pack`) write only derived `clued_private.context_pack_manifests` rows (digests, source versions, stale flag; no pack bodies, no Receipt). A manifest or pack is never Canonical truth or an online fallback. Policies are never Markdown or repository files.
- Information Flow Evidence withdrawal and invalidation (S5): `clued_evidence_withdrawal_confirmation_issue_v1` (step 1, REST `POST /v1/evidence/{id}/withdrawal/confirmation`) and `clued_evidence_withdraw_v1` (step 2, REST `POST /v1/evidence/{id}/withdrawal`) are Native account-session RPCs only (`authenticated`, `authorization_owner_v12`; never an MCP tool, OAuth case or Binding, even for Evidence a Binding ingested). Withdrawal is the receipt-core family `evidence_withdraw`; its CAS is the `clued_private.evidence_withdrawals` row `version` (`base_version` 0 before the first withdrawal; withdrawal is terminal in MVP-0). Issuing writes no Receipt and stores only the hash of a single-use token in `clued_private.native_confirmation_tokens` with `action='evidence_withdraw'` (5-minute TTL, session authenticated within 15 minutes, bound to user, Evidence id, base version, session and the view digest over the Evidence descriptor and reason). The Evidence row is never modified or deleted. In one transaction the withdrawal moves dependent pending candidates to `conflict` (candidate row-version CAS, same Receipt), flags every Record whose current `source_refs` cite the Evidence in `clued_private.record_evidence_status`, flags `clued_private.knowledge_lineage`, marks dependent `context_pack_manifests` stale, and emits the audit-only `extension:information_flow:evidence_withdrawn` Event. `knowledge_lineage` is seeded only from `candidate_promotions`; triggers on Record changes, `record_evidence_status`, lineage and Binding authorization changes write only lineage flags or manifest stale flags and never modify a Canonical Record. `lineage_stale` and `evidence_withdrawn` affect MSCP compilation only (the Record still reads CURRENT/active elsewhere) and are lifted only by a new Receipt-backed promotion or a re-sourced version written through `record_mutation_with_terminal_guard`. An Event with the same extension name appended by any caller changes no withdrawal, candidate, lineage or policy state.
- Information Flow confirmation-token hardening (`20260925000000_information_flow_token_hardening.sql`; A03 L29, L30, B09 round 3 F01), for the S3, S4 and S5 two-step tokens: a token is issued only to an account-session JWT whose `session_id` claim is a non-empty string; otherwise step 1 is rejected with `confirmation_token_session_id_required` and no token row is written. Step 2 requires the stored token `session_id` to be non-null and equal to the JWT's (else `confirmation_token_binding_mismatch`). The S4 and S5 consume paths look tokens up in `clued_private.native_confirmation_tokens` only for their own `action` (`context_policy_accept`, `evidence_withdraw`), so a token for one action reads `confirmation_token_invalid` at the other action's RPC and is not burned; a same-action token presented for another subject is still burned as a binding mismatch. S3 promotion, like S4 acceptance and S5 withdrawal, locates a presented token before any input-shape check, so every attempt that reaches the receipt core with a live token burns it, including malformed requests; failures before the receipt core still do not burn (L11).
